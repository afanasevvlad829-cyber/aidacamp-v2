# cohort-forecast — прогноз «горячих» лидов по поведению на сайте

Живёт на сервере в `/opt/cohort-forecast/` (не в деплое сайта — отдельный
процесс, крутится по крону, БЕЗ git до этого коммита — здесь только
снапшот для истории/документации).

## Что делает `daily.py`

Раз в сутки (`/etc/cron.d/cohort-forecast`, `30 5 * * * root` — 08:30 МСК):

1. **Валидация** — проверяет клиентов из предыдущих когорт: достигли ли цели
   в Метрике или появились в AlfaCRM с меткой `ymCid:` → помечает `converted`.
2. **Добор топ-25** — берёт посетителей за последние 7 дней с `visits>1`
   (Reporting API Метрики), которые ещё не оставляли заявку, ранжирует по
   `visits + pageviews*0.5 + seconds/120`, берёт топ-25, классифицирует
   тиром (`hot`/`warm`/`cold`) и кладёт в `cohort_forecast`.
3. **Обновление портрета** — раз накопится ≥5 подтверждённых покупателей,
   пересчитывает медианы (`buyer_portrait`) — визиты/просмотры/секунды.

## Известное ограничение — раз в сутки

Крон разовый (08:30 МСК). Лиды, которые доходят до заявки **в тот же день
позже этого времени**, физически не могут попасть в когорту дня — модель
их ещё не видела. Также лиды с ровно 1 визитом никогда не станут
кандидатами (`filters=ym:s:visits>1` в part B) — конверсия с первого же
захода в принципе не отслеживается этой моделью. Это не баг, а архитектурное
ограничение батч-процесса — не чинили в рамках этой правки.

## 2026-07-02 — коррекция порога `hot`

**Повод:** реальный лид (CRM #5233→5232, см. `client_attribution`) —
2 визита (30.06 + 02.07), 11 просмотров, ~1882 сек суммарно. По старым
порогам классифицировался как `warm`, а не `hot`, хотя вовлечённость
явно высокая — просто визитов чуть меньше «стандартных» 3.

**Что было:**
```python
if v>=max(3,PV) and sec>=2000: return 'hot',0.45
```
`PV` — медиана визитов у подтверждённых покупателей (`buyer_portrait`,
на 02.07 = 3). `max(3,PV)` держит пол в 3 визита независимо от PV.

**Что стало:**
```python
if v>=2 and sec>=1800: return 'hot',0.45
```
Убрали зависимость от `PV` для этого порога — раньше `max(2,PV)` тоже не
сработал бы, пока PV=3 (max(2,3)=3, порог не менялся бы). Захардкодили
`v>=2`. Секунды снижены с 2000 до 1800.

С новыми порогами упомянутый лид (v=2, sec=1882) попадает в `hot`.

**Оговорка:** решение на N=1 (один лид), не на статистике. Порог `sec`
для `hot` не учитывает глубину (`pageviews`) — теоретически можно попасть
в `hot` с 2 визитами и малым числом страниц, но долгим временем (открытая
вкладка). Тот же паттерн был и раньше (`sec>=2000` тоже не проверял
глубину) — не меняли эту часть логики, чтобы не расширять правку.

## Применение

Правка внесена вручную на сервере (`/opt/cohort-forecast/daily.py`) и
здесь одновременно — скрипт не деплоится из git, крон запускает файл
напрямую с диска, поэтому снапшот в репозитории — для истории, а не
источник правды в проде.
