# Google Analytics — идентификаторы и Measurement Protocol

Заведён 01.08.2026. Про GA4 на сайте: где живёт счётчик, как достаём client_id, как
отправляем оплаты серверно. Метрика — в отдельном файле [Аналитика — Метрика и боты](Аналитика%20—%20Метрика%20и%20боты.md).

## Где счётчик

- Идентификатор потока: `G-PGMT3ET16X`.
- Единственное место загрузки — `src/components/GoogleAnalytics.astro`. Не вставлять
  сниппет gtag в страницы руками: разъедется, как разъезжались цены до `shifts.ts`.
- Два режима компонента:
  - ленивый (по умолчанию, `Base.astro`) — после `window.load`, в ближайший idle, но
    не позже 3 с, плюс мгновенно по первому взаимодействию;
  - `immediate` — грузим сразу. Стоит на памятке `/p/[lid]`: там куки `_ga` нужна
    привязке визита к карточке CRM уже на 1,5-й секунде, а страница `noindex`.
- Бот/dev-хост/внутренние пути отсекаются флагом `window._clarityDisabled`, он
  ставится в `Base.astro`. На автономных страницах флага нет — гейт не срабатывает.

## client_id: главная грабля

Куки `_ga` имеет вид `GA1.1.1234567890.1699999999`.

**client_id для GA4 — это ДВА последних сегмента целиком: `1234567890.1699999999`.**
Не только первое число. Measurement Protocol с усечённым id ответит 204 (он всегда
отвечает 204), но событие в отчётах не появится — тихая потеря данных.

Хвост `1699999999` — unix-время первого визита, из него берём дату первого захода.

## Зачем второй идентификатор

Связка «визит → карточка клиента» на памятке держалась на одном `ym('getClientID')`.
Не отдался (блокировщик, приватный режим, сбой) — визит терялся целиком. Теперь рядом
пишется `ga_client_id` из куки `_ga`: второй независимый шанс на матч.

Отсутствие куки — **не ошибка**: GA грузится асинхронно, привязка стреляет на 1,5 / 4,5 / 9 с.
Пишем что есть; повторная отправка ровно одна — когда куки появилась (гард
`pm_bound_<lid>` хранит отметку «был ли ga_client_id»).

Колонки в `pamyatka_bindings`: `ga_client_id`, `ga_first_visit`, `gclid`.

## Measurement Protocol: отправка оплат

Скрипт — `scripts/ga-purchase-mp.mjs`, кроном раз в час на проде.

- Источник денег: `crm_payments`, **только `pay_type_id = 1`** (приход). 7 — расход,
  есть ещё 5 и 8 — их не шлём.
- Связь платежа с визитом: `crm_payments.customer_id` → `pamyatka_bindings.crm_id` →
  последний непустой `ga_client_id` (менеджерские привязки исключены).
- Идемпотентность двойная: таблица `ga_mp_sent (branch, payment_id)` + `transaction_id`
  вида `alfa-<branch>-<id>` на стороне GA.
- Событие уходит **без `timestamp_micros`**, то есть датируется моментом отправки.
  Причина: MP не принимает бэкдейт старше 72 часов, а `pay_date` — дата без времени,
  так что трёхдневный платёж уехал бы в отказ. Отсюда требование к крону — раз в час.
- Окно выборки — `GA_MP_WINDOW_DAYS` (по умолчанию 7 дней), чтобы новый матч по старой
  оплате не вылил в GA историю.
- Отладка: `--dry-run` (ничего не шлёт) и `--debug` (debug-эндпоинт GA, показывает
  ошибки валидации; боевой эндпоинт молча отвечает 204 на что угодно).

### API secret создаётся руками

Ключ нельзя получить через API. GA4 → **Администратор** → **Потоки данных** → поток
`aidacamp.ru` → **Measurement Protocol API secrets** → **Создать**. Значение — в
`/var/www/aidacamp/.env.prod` как `GA4_MP_API_SECRET` (сайт читает только этот файл).

## GA360 — не нужна

Владелец спрашивал. Платная GA360 российским юрлицам не продаётся, и главное — выгрузка
в BigQuery, ради которой её раньше брали, с 2023 года доступна в **бесплатном** GA4
(Администратор → Связи с продуктами → BigQuery). Отдельная тема: BigQuery требует
проекта в Google Cloud и платёжного аккаунта — заводить только по отдельному решению.

## gclid

Ловим на памятке (из URL, иначе из сохранённой атрибуции `ac_attribution`) и пишем в
`pamyatka_bindings.gclid`. В Measurement Protocol его передавать бессмысленно — GA4 не
принимает gclid как параметр события. Он нужен для офлайн-конверсий Google Ads, это
отдельный механизм (Google Ads API / загрузка конверсий), в России сейчас неактуален.
