# Правило по шрифтам — рилсы АйдаКодить/АйДаКемп

Выведено из фидбека владельца на пилотах 1-5 (02.09.2026) — «мелкий шрифт» повторялось
четыре раза подряд, пока размеры не дошли до цифр ниже. Дальше — используй их как пол,
не как потолок: если конкретный кадр всё равно выглядит мелко, поднимай ещё, не оглядывайся
на «уже же большой».

## Главный визуальный ориентир

Самая широкая строка текста в кадре должна занимать **~75-90% ширины холста** (1080px),
не 50-55%. Если после ввода текста в композицию строка визуально «тонет» в кадре с
большими полями по бокам — шрифт мелкий, независимо от px-значения.

## Минимальные размеры (1080×1920, вертикаль)

| Элемент | Минимум | Комментарий |
|---|---|---|
| Хук-заголовок (1-3 слова/строка) | **110-120px**, до 140px если фраза короткая | Проверяй через `hyperframes check` на `canvas_overflow` — если вылезает за края, не уменьшай сгоряча весь размер, сначала попробуй разбить фразу на дополнительную строку |
| Основной текст сцены (2-4 строки) | **90-96px** | Это самый частый источник жалобы «мелко» — сюда чаще всего забывают вернуться после хука |
| CTA-утверждение | **76-80px** | |
| CTA-вопрос (последняя реплика) | **62-66px** | |
| Крупная цифра/статистика (герой-число: +48%, бар-значение) | **90-130px**, шире — если позволяет колонка | Проверяй `content_overlap` между соседними колонками при таких размерах |
| Киккер/рубрика (мелкая надпись-ярлык) | 34-40px | Единственный элемент, которому положено быть мелким — это подпись, не основной месседж |
| Бренд-тег `@aida_codit` внизу | 26-30px | Тоже намеренно мелкий, не считается |

## Порядок действий при любом новом ролике

1. Bерстаешь текст на глаз крупным — не экономь место «про запас».
2. `npx hyperframes check` — это единственный способ поймать переполнение/наложение
   до рендера. Если есть `canvas_overflow` или `content_overlap` — правь **компоновку**
   (разбить строку, сузить колонку, поднять контейнер), а не автоматически уменьшай шрифт
   до исчезновения ошибки. Уменьшение — крайний случай.
3. После правки — снова `check`, потом рендер `--quality draft`, вытащи стоп-кадр
   (`ffmpeg -ss <t> -vframes 1`) и посмотри сам через Read, крупно ли выглядит —
   не полагайся только на «числа больше, чем в прошлый раз».
4. Только после самопроверки — рендер `--quality high` и отправка владельцу.

## Известные технические ловушки (чтобы не наступать заново)

- **CSS `transform` + GSAP-твин на том же свойстве** (например статичный
  `transform: scaleX(0)` в CSS и `.to(..., {scaleX: 1})` в скрипте) — GSAP молча
  перезаписывает transform, линт ловит это как `gsap_css_transform_conflict`.
  Начальное состояние всегда через `tl.set(...)`, не через CSS.
- **Анимация layout-свойств** (`top`, `left` и т.п.) вместо transform (`x`, `y`) —
  дёргается при покадровом рендере, линт ловит как `gsap_non_transform_motion`.
- **Декоративные полупрозрачные слои (виньетка и т.п.) должны стоять по z-index НИЖЕ
  текста**, не выше — иначе чекер (и глаз) ловит текст как перекрытый
  (`text_occluded`), особенно когда шрифт вырос и строки стали доставать до края кадра.
