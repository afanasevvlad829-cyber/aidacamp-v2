# ТЗ: Аудит кодовых баз всех сайтов — aidacamp, codims, icepartners, vlad-a

**Дата:** 2026-07-15 · **Тип:** исследование, read-only (ни одной правки кода) · **Заказчик:** владелец проекта

---

## 1. Цель

Получить полную, приоритизированную картину технического состояния кодовых баз **всех четырёх
сайтов**: эффективность кода, дубликаты, хардкод, мёртвый код, модульность, возможности
сокращения объёма кода и оптимизаций — в виде отчёта с бэклогом конкретных задач, каждая с
рекомендацией (минимальным действием), оценкой эффекта, трудозатрат и риска.

**Не цель:** рефакторинг. Аудит ничего не меняет. Фиксы — отдельными задачами по итогам.

### 2.1. vlad-a.ru — особый случай

На сервере лежит только собранный вывод (`dist`), git-репозитория нет. Порядок:
1. Первым делом выяснить, где исходники (поискать на сервере и на маке; спросить владельца).
2. **Отсутствие исходников/репозитория — само по себе находка P0** (сайт невозможно
   пересобрать → риск полной потери при инциденте): зафиксировать в отчёте с рекомендацией
   (восстановить исходники или принять «прод = источник» и положить его под git + бэкап).
3. Аудит по факту прода: runtime-метрики (4.6), хардкод в html, вес `_astro/`-бандлов,
   дубли между 46 страницами. Read-only по SSH, ничего на сервере не менять.

## 3. Границы и жёсткие «НЕ ТРОГАТЬ»

Рекомендации, нарушающие эти пункты, бракуются на приёмке.

**Для всех сайтов:** перед аудитом каждого репо прочитать его `CLAUDE.md`/`AGENTS.md` — там
свои правила и инциденты. На codims недавно прошли SEO-волны с массовыми редиректами —
любые предложения слияния/удаления страниц там проверять против текущих позиций (Топвизор),
как и правило по лендингам aidacamp ниже.

**Для aidacamp.ru:**

1. **182 SEO-лендинга — НЕ предлагать массовый перенос в `[slug].astro`.** Это сознательная
   SEO-политика (уникальные тексты против шаблонного дублирования, см. CLAUDE.md и
   `src/data/seasons.ts`). Дублирование *текстов* между лендингами — допустимое. Аудит ищет
   только *техническое* дублирование: одинаковые блоки разметки/логики, которые можно вынести
   в компонент без унификации текстов.
2. **`@astrojs/partytown` — запрещённая зависимость**, не предлагать (инцидент 04.2026, −60К₽).
3. Единый источник цен/дат: `src/data/shifts.ts` (`SHIFT_META`) + `src/data/dynamicPrices.ts`.
   Стражи `check:prices` / `check:dates` / `check:banned` — часть билда. Аудит проверяет
   их обходы, но не предлагает менять архитектуру источника.
4. Страница «Тревожный родитель» — сатира, фейковые отзывы намеренны (не «баг контента»).
5. Дизайн-система — только `DESIGN_SYSTEM.md`; иконки — только Bootstrap Icons из
   `src/data/icons-manifest.json`.

## 4. Направления аудита (обязательные блоки отчёта)

Блоки применяются к каждому сайту согласно глубине из таблицы раздела 2 (примеры и цифры
ниже даны по aidacamp как основному объекту; для codims/icepartners — те же проверки в их
масштабе, для vlad-a — режим из 2.1). Отдельный сквозной пункт: **дублирование МЕЖДУ
сайтами** — компоненты/утилиты, скопированные из aidacamp в codims/icepartners
(кандидаты в общий пакет — только как рекомендация, без внедрения).

### 4.1. Дубликаты кода
- Прогнать `jscpd` по `src/` (пороги: ≥30 строк или ≥150 токенов), отдельно по `.astro` и `.ts`.
- Ручная проверка топ-20 клонов: техническое дублирование (вынести в компонент/утилиту)
  или SEO-намеренное (пометить и исключить).
- Отдельно: дублирование между 72 API-endpoints (общие куски валидации, подключения к PG,
  обработки ошибок → кандидаты в `src/lib/`).
- **Инлайн-`<script>` — главная Astro-специфичная зона проекта** (293 файла со скриптами при
  всего 10 `client:`-директивах): найти повторяющиеся скрипты между страницами/лендингами
  (аккордеоны, слайдеры, формы, счётчики), оценить объём дублируемого JS в `dist/`,
  предложить кандидатов на вынос в общие модули `src/scripts/` — без изменения поведения.

### 4.2. Хардкод
- Цены/даты смен вне `shifts.ts`/`dynamicPrices.ts` (сверх того, что ловят стражи —
  проверить сами стражи на слепые зоны: JSON-файлы, `src/data/landings/`, schema.org-разметка).
- Суммы налогового вычета литералами (правило: только «до 6 200 ₽ (максимум, Смена 1)»).
- URL/домены, телефоны, ID Метрики/целей (541048270, 541048197), ID кампаний Директа литералами.
- Цвета/размеры вне токенов дизайн-системы, inline-стили в компонентах.
- Абсолютные пути к серверным ресурсам в клиентском коде.
- Env-гигиена Astro: значения, которые обязаны быть в env, но зашиты в код; и наоборот —
  секреты в `PUBLIC_*`-переменных (они попадают в клиентский бандл; проверить в т.ч.
  `src/pages/api/tts.ts`); feature-флаги литералами.

### 4.3. Мёртвый код
- Компоненты, которые никто не импортирует (прямой обход импортов; ⚠️ граф-инструменты
  codebase-memory/socraticode `.astro` не парсят — только grep/скрипт + субагенты).
- `src/_archive/`, `src/pages/prototype/`, `src/pages/demo/` — что из этого попадает в билд
  и индексацию; вес в `dist/`.
- Неиспользуемые exports в `src/lib/`, `src/utils/`, `src/data/` (`knip`).
- API-endpoints без единого вызывающего (grep по репо + логи nginx за 30 дней на сервере).
- `scripts/` — скрипты, не упоминаемые ни в package.json, ни в cron, ни в docs.

### 4.4. Зависимости
- `knip`/`depcheck`: неиспользуемые из 22 prod-зависимостей (проверить кандидатов: `mammoth`,
  `sortablejs`, `@uppy/*`, `plyr` — где реально используются и грузятся ли глобально).
- Вес клиентского JS: что попадает в бандл каждой страницы (`astro build` + анализ `dist/`),
  тяжёлые библиотеки на страницах, где они не нужны.
- Дубли функциональности (например `dayjs` vs ручная работа с датами).

### 4.5. Модульность и архитектура
- Компоненты-гиганты (>500 строк) — список, что выносится.
- Смешение слоёв: обращение к PG/данным прямо из `.astro`-страниц в обход `src/lib/`.
- Логика, скопированная между `src/pages/api/` и ботом/скриптами.
- Циклические зависимости в `.ts` (`madge`).
- `src/partials/` vs `src/components/` — есть ли внятная граница, дубли между ними.
- Слой данных: content collections используются только для `articles` — проверить, где рядом
  живут параллельные механизмы (прямые импорты `src/data/*.json`, генерация `articles.json`
  скриптом + schema в `content.config.ts`) и есть ли данные, дублируемые в двух форматах.
- 10 существующих `client:`-директив: оправдана ли hydration в каждом случае
  (или хватит статики/инлайн-скрипта) — маленький, но обязательный чек.

### 4.6. Производительность билда и рантайма
- Время `npm run build` (замер ×3), самые медленные шаги; вклад `@playform/compress`, pagefind.
- Размер `dist/`, топ-20 тяжёлых страниц по HTML+JS.
- SSR-endpoints (`@astrojs/node`): блокирующие запросы, отсутствие таймаутов к PG/внешним API.
- **Runtime-метрики прода** (базовая линия «до»): TTFB, LCP, CLS, INP, вес страницы и число
  запросов для топ-10 страниц по трафику — через MCP `run(service="pagespeed")` +
  `run(service="clarity")`; порядок загрузки CSS/JS, блокирующие ресурсы, split chunks,
  `prefetch`/`preload`, lazy loading изображений, кэширование. Зафиксировать в отчёте —
  это точка отсчёта для будущих фиксов.

### 4.9. Безопасность (отдельный раздел отчёта)
- **icepartners.ru (обязательно):** отдельный express-сервер (`server/`) — авторизация его
  endpoints, `multer`-загрузка файлов (тип/размер/куда пишется), `nodemailer` (инъекции в
  заголовки писем, кто может триггерить отправку), где живёт ключ `@anthropic-ai/sdk`.
- aidacamp: 72 API-endpoints — на каких отсутствует проверка авторизации (особенно всё под
  `src/pages/api/`, что пишет в PG или файлы); доступ к `admin/`, `dashboard/`, `staff/`,
  `portal/` — как защищены (middleware.ts?).
- Валидация входа: где используется `zod`, а где параметры летят в запросы без валидации
  (риск инъекций в `pg`-запросах — параметризация везде?).
- Загрузка файлов (`@uppy/*` → endpoint): ограничения типа/размера, куда пишется, доступность
  залитого извне.
- Секреты в клиентском коде и в git (ключи API, токены в `.astro`/`public/`).
- Rate limiting на публичных формах (`/api/lead` и подобных); спам-защита.
- Формат результата: критичные уязвимости — отдельным списком P0, каждая с файлом,
  сценарием эксплуатации и минимальным фиксом.

### 4.7. Качество и стражи
- `astro check` + `tsc --noEmit`: количество и категории ошибок типов.
- Покрытие тестами: что покрыто vitest/playwright сейчас, критические непокрытые зоны
  (`dynamicPrices` покрыт — что ещё обязано быть: API `/api/lead`, бот `campData`).
- Слепые зоны стражей `check:*` (см. 4.2).

### 4.8. Сводный потенциал сокращения
- Оценка в строках/файлах: сколько кода реально можно удалить или схлопнуть без риска
  (мёртвый код + технические дубли + архив), с разбивкой по направлениям.

## 5. Методика

1. Работа — в изолированном окружении: `./scripts/agent-docker.sh` или worktree через
   `./scripts/agent-start.sh` (аудит read-only, но правило №1 действует). Замеры билда — там же.
2. Инструменты ставить локально в окружение аудита (`npx jscpd`, `npx knip`, `npx madge`),
   в `package.json` проекта ничего не добавлять.
3. Каждый вывод — **факт со ссылкой** `файл:строка` или командой воспроизведения.
   Гипотезы помечать явно («гипотеза»). «Не найдено» — честный допустимый результат.
4. Долгие прогоны (build ×3, jscpd по 565 файлам) — фоном с логом, не блокирующим вызовом
   (правило из CLAUDE.md «Долгие операции»).

## 7. Критерии разумной достаточности (когда остановиться)

Аудит достаточен, когда дальнейшее углубление уже не меняет приоритеты ближайших решений:
- проверены все зоны раздела 4; для каждой критичной находки есть место, причина, риск
  и минимальное действие;
- НЕ требуется: анализ исторических веток и `src/_archive/` глубже вопроса «попадает ли в
  билд»; стопроцентная проверка каждого из 182 лендингов (достаточно выборки + автоматики);
- оптимизация не рекомендуется, если ожидаемый выигрыш меньше риска изменения;
- новый модуль/сервис не предлагается, если текущую архитектуру можно безопасно расширить;
- работа останавливается после появления понятного бэклога с приоритетами и оценкой риска.
