# ТЗ: Инвентаризация MCP-инструментов, единый каталог, токены и мониторинг доступности

**Дата:** 2026-07-15 · **Тип:** инфраструктурная задача (инвентаризация → консолидация → мониторинг)
**Репозиторий работ:** `~/MCP` (ветка `main`) + сервер `aidacamp-prod` (159.194.223.55)

---

## 1. Цель

Собрать все инструменты экосистемы (MCP-сервисы, скрипты, cron-ы, systemd-юниты) в **один
управляемый пакет** с:
1. **Единым каталогом-реестром** — машиночитаемый список всех инструментов с владельцем,
   секретами и способом проверки;
2. **Единым репозиторием токенов** — один источник правды для секретов, ноль разброса по .env;
3. **Единым мониторингом доступности** — ночной cron проходит по всем инструментам,
   проверяет доступность и шлёт уведомление, если что-то упало.

## 3. Фазы работ

### Фаза 1 — Инвентаризация (read-only)

Обойти и свести в реестр:
- `GET /mcp/api/tools` + `/opt/mcp/lib/run/*` (каждый сервис: actions, какие env-переменные читает — grep по `process.env`);
- `~/MCP/` (server.mjs, social-poster, скрипты) и расхождения local vs server;
- `crontab -l` root + `/etc/cron.d/*` на сервере; `systemctl list-units --type=service,timer`
  (свои юниты: mcp, tg-debug, telegram-max-sync, agent-browser, netdata и т.д.);
- launchd-агенты на маке (`~/Library/LaunchAgents/ru.aidacamp.*`);
- все `.env*` в `/opt/**` и «кто их читает» (grep по путям в коде/юнитах/cron).

**Результат:** `~/MCP/registry/tools.yaml` — по одной записи на инструмент:

```yaml
- id: direct
  kind: mcp-service            # mcp-service | script | cron | systemd | launchd
  layer: server                # server | mac | both
  entry: /opt/mcp/lib/run/direct.mjs
  actions: [campaigns, adgroup, ad, keywords, stats, bids]
  secrets: [DIRECT_TOKEN]      # имена из secretctl/env, НЕ значения
  probe:                       # как проверить живость (см. Фаза 3)
    call: {service: direct, action: campaigns, params: {limit: 1}}
    timeout_s: 15
  status: active               # active | broken | blocked-owner | deprecated
  criticality: high            # high (бизнес встаёт) | medium | low
  last_verified: 2026-07-15    # обновляется автоматически health-check-ом
  notes: ""
```

Из `tools.yaml` генерировать человекочитаемую сводную таблицу в `TOOLS.md`
(секция «Каталог инструментов», автоген-маркерами) — руками её больше не править.

### Фаза 2 — Консолидация токенов

Принцип: **один источник правды на слой**, всё остальное — производное.
- Сервер: канон — `/opt/aidacamp-tools/etl/.env`. Остальные .env либо генерируются из него
  скриптом `sync-env.sh` (белый список переменных на каждый потребитель — не копировать все
  ключи всем), либо заменяются симлинком, если потребителю нужен весь набор.
- Мак: канон — `secretctl` (уже есть). Задача — сверить: каждый секрет из .env-файлов
  представлен в secretctl, имена совпадают с таблицей в `TOOLS.md`.
- Результаты: карта «секрет → где лежит → кто читает» (в реестре, поле `secrets`),
  `env.template` с именами без значений в git, отчёт о расхождениях (секреты-сироты,
  дубли под разными именами, просроченные).
- Реестр секретов `~/MCP/registry/secrets.yaml` (только метаданные, без значений):
  `имя | назначение | где используется | владелец | как проверить | срок действия /
  признаки протухания | процедура ротации | критичность`. Для токенов с известным сроком
  жизни (VK, Яндекс OAuth) — поле `expires` и напоминание в еженедельный дайджест за 14 дней.
- **Жёстко:** ни одно значение токена — в git, в логи, в отчёты, в чат. Только имена.
  Права на .env: `600`, владелец сервиса.

### Фаза 3 — Health-check runner

Скрипт `/opt/scripts/mcp-healthcheck.sh` (+ `healthcheck.mjs` рядом с MCP):
- Для каждой записи `tools.yaml` со `status: active` выполняет **неразрушающий read-only
  probe** из поля `probe`: для MCP-сервисов — лёгкий вызов через `POST /mcp/api/call`
  (list/read с `limit:1`), для systemd — `systemctl is-active`, для cron — свежесть
  лог-файла/маркера, для HTTP — `curl -m 10 -o /dev/null -w '%{http_code}'`.
- Probe НИКОГДА не пишет/не удаляет (для Я.Диска в принципе только чтение; правило
  `permanently=false` не трогать).
- Таймаут на probe ≤ 15 с, весь прогон ≤ 5 мин; probes независимы — падение одного не
  прерывает остальные.
- Результат: `/var/log/mcp-health/YYYY-MM-DD.json` — `{id, ok, latency_ms, error}` по каждому
  + сводка. Ошибки без значений секретов (санитизация вывода curl/API).

### Фаза 4 — Ночной cron + уведомления

- **systemd timer** `mcp-healthcheck.timer` (04:15 МСК, `Persistent=true`) + сервис с
  cgroup-лимитами (`MemoryMax=300M`, `CPUQuota=50%`) — сервер ограничен (5.8 ГБ RAM, диск 90%+),
  перед установкой проверить `free -h` и `df -h`.
- Запуск — **фон + лог**, никакого ожидания внутри одного вызова (правило CLAUDE.md
  «Долгие операции»).
- Уведомления — через существующий сервис `telegram` самого MCP (`run(service="telegram")`);
  если упал сам MCP-сервер — фолбэк: прямой вызов Telegram Bot API из скрипта
  (токен из канонического .env).
- Логика алертов:
  - **анти-дребезг:** при ошибке probe — повторная проверка через 5 минут (отдельным запуском
    по таймеру/`systemd-run --on-active`, не sleep внутри вызова); алерт только по
    подтверждённой ошибке — одиночный сетевой чих не будит;
  - что-то упало → одно сообщение со списком упавших (id, ошибка, latency);
  - продолжает лежать → ежедневный дайджест «still down: N день» (не молчать, но не спамить
    отдельными сообщениями);
  - всё поднялось → однократное «recovered»;
  - всё ок → тишина (ничего не слать).
- Ротация логов: держать 30 дней (`find -mtime +30 -delete` в том же юните).

### Фаза 5 — Витрина статуса (минимальная)

- Расширить `GET /mcp/api/channel-status` (или добавить `/mcp/api/health`) — отдавать
  последний JSON прогона.
- Разовый отчёт об итогах всей задачи (реестр, карта токенов, скрин работы алерта) —
  в Reports Hub, категория `other`, теги `mcp,monitoring`.

## 3.1. Принцип разумной достаточности

Мониторинг начинается с простого healthcheck + уведомлений. Никаких observability-платформ
(Prometheus/Grafana/Zabbix), отдельных БД истории и «сложных дашбордов» — пока простая схема
не докажет свою недостаточность. История статусов = 30 дней JSON-логов, этого хватает.
Каталог = один `tools.yaml` + автоген-таблица в `TOOLS.md`; отдельные папки-манифесты на
каждый инструмент не заводить — плодят рассинхрон.

## 4. Ограничения и правила

1. Перед предложением «нового инструмента» — grep `/opt/mcp/lib/run/` и SEO-TOOLS-STACK.md:
   возможно, он уже есть (правило проекта).
2. Никаких блокирующих `sleep` в вызовах; всё долгое — nohup/systemd + лог + короткие проверки.
3. Новые процессы — на сервере, не на маке (8 ГБ RAM); systemd-юниты только с лимитами.
4. Probes только read-only; сервисы с ценой за вызов (arsenkin, dataforseo, pagespeed) —
  probe без списания лимитов, где невозможно — проверка раз в неделю, не каждую ночь
  (поле `probe.schedule: weekly` в реестре).
5. Просроченные токены, требующие OAuth владельца (YADISK) — не «чинить», а пометить
   `blocked-owner` и включить в алерт-дайджест один раз в неделю.
6. Коммитить сразу в `~/MCP` (main); изменения на сервере — фиксировать в `~/MCP/docs/`.
