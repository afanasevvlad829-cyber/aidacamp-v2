# Онбординг: фото ребёнка → Immich Person → `room_assignment` — Дизайн (Фаза 2, спек 1 из 4)

**Дата:** 2026-07-28
**Статус:** Approved
**Область:** разовый (на каждую смену) этап привязки эталонного фото ребёнка к его записи в расселении, через тот же `@Aidacamp2026bot`. Первый из четырёх кусков «ИИ-обработки» (см. декомпозицию ниже) — без него распознавание лиц на черновиках (спек 2) не работает.

## Место в общей декомпозиции «ИИ-обработки» (Фаза 2)

1. **Этот спек** — онбординг: фото ребёнка → Immich Person → `room_assignment`
2. Face-match новых черновиков (из Фазы 1) против базы, собранной в (1)
3. Контекст дня — реальное меню/расписание/события смены как факты для шуток (5–6 волн публикаций в день, не одна вечерняя)
4. Генерация текста (Grok, «Fun Mode», vision) — сборка (2)+(3) в шутливую подпись голосом Дарьи, подставляется в `draft_post.text` из Фазы 1 до отправки руководителю на ревью

Каждый пункт — отдельный спек → план → реализация.

## Источник детей: `room_assignment`, не `portal_kid`

В портале есть два параллельных списка детей:
- `portal_kid` — используется для ученического логина по 6-значному коду
- `room_assignment` (модуль `/portal/rooms`) — живой ростер смены, синкается с AlfaCRM через `/api/shift-roster?shift=N` (группа 660–665 = Смены 1–6, филиал 5 CAMP). **Проверено живым запросом на dev и prod (2026-07-28)** — оба вернули реальные 13 детей группы 660.

**Для онбординга источник — `room_assignment`**, потому что именно туда дети загружаются из AlfaCRM (кнопка «Синк из CRM» на `/portal/rooms`). `kid_id` в этой таблице — `alfaId` (строка), `kid_name` — полное ФИО в формате «Фамилия Имя Отчество» (фамилия первым словом — удобно для поиска).

`room_assignment` пересоздаётся на каждую смену (`UNIQUE shift_id + kid_id`), поэтому привязка к Immich Person **тоже живёт посменно** — без отдельной постоянной таблицы «лицо ребёнка» между заездами. Возвращающийся в другую смену ребёнок будет пере-помечен заново. Это сознательное упрощение для Фазы 2; хранение лица между сменами — возможное расширение позже, не сейчас.

## Режим бота

`/анбординг` переключает `@Aidacamp2026bot` из режима «черновик для родителей» (Фаза 1) в режим «довязка фото к ребёнку». `/анбординг_стоп` — выход. Пока бот не переключён обратно, входящие фото трактуются как онбординг, а не как черновик поста — это разные состояния одного и того же диалога с сотрудником, взаимоисключающие.

Доступно любому активному `portal_staff` (`vozhaty`/`teacher`/`rukovoditel`/`admin`).

Привязка к смене: при входе в `/анбординг` бот использует активную смену (`shift.status='active'`). **Предположение, требует подтверждения в плане реализации:** что активная смена всегда одна — если камп может вести две смены параллельно (пересменка), команда должна явно указывать `shift_id`.

## Поток на одного ребёнка

1. Сотрудник шлёт **фото** (обычное, сжатое — при онбординге скорость важнее исходного качества файла, в отличие от черновиков Фазы 1).
2. Бот просит фамилию — сотрудник отвечает **голосом или текстом**.
   - Голос → расшифровка через OpenAI Whisper API (`whisper-1`, `language=ru`), прямой вызов из Astro-бэкенда, тот же `OPENAI_API_KEY`, что уже используется в проекте (`DaryaAgent`/`intelligence/whisper.py` на сервере — здесь используем API напрямую, без зависимости от того Python-сервиса).
3. Бот ищет `room_assignment.kid_name ILIKE '%<фамилия>%'` среди детей активной смены, показывает **тап-список** кандидатов (просто ФИО — без номера комнаты: расселение меняется много раз после старта смены и не годится как ориентир на этом этапе).
4. Сотрудник **тапает** нужного — только по явному тапу происходит привязка, даже если совпадение было ровно одно.
5. Ноль совпадений → «не нашёл, попробуйте иначе» — присланное фото остаётся ждать, повторно слать не нужно.
6. Много совпадений (частая фамилия) → показываю первые ~10, прошу уточнить полнее.
7. После тапа: фото загружается в Immich, запускается распознавание лица, создаётся/переиспользуется Person, присваивается имя → `room_assignment.immich_person_id` (новая колонка) сохраняет связь.

Состояние «есть фото, жду фамилию/тап» хранится по `telegram_id` сотрудника до момента тапа.

Если у ребёнка в этой смене уже стоит `immich_person_id` (переонбординг/исправление) — новое фото просто обновляет привязку, не создаёт дубль Person.

## Immich-интеграция — не проверено, первая задача плана реализации

Точная механика Immich API для «загрузить фото → дождаться детекции лица (асинхронная ML-джоба) → создать/переиспользовать Person → присвоить лицо этому Person» не подтверждена против текущей версии Immich на сервере (`/opt/immich`, `photos.aidacamp.ru`). Известно из `IMMICH_API_KEY` (`/opt/mcp/.env`) и общих эндпоинтов (`/api/albums`, `/api/assets`), но не проверены: `/api/people` (создание/переименование), назначение обнаруженного лица конкретному Person, и реальное время ожидания детекции. Без этой проверки код загрузки и привязки не пишется.

## Обработка ошибок

- Whisper не смог распознать / вернул мусор → бот просит повторить голосом или написать текстом.
- Immich недоступен / upload упал → бот сообщает об ошибке сотруднику, фото остаётся в состоянии «жду», можно повторить попытку без пересылки фото и фамилии заново (если технически возможно переиспользовать уже полученный файл; иначе — явно попросить прислать фото повторно, это уточняется в плане реализации вместе с проверкой Immich API).

## Тестирование

- Юнит-тесты: парсинг фамилии из голоса/текста, ILIKE-поиск с несколькими/нулевым числом совпадений, ограничение списка до ~10.
- Ручной smoke-тест на dev-боте: полный цикл фото → голос → тап → появление `immich_person_id` в `room_assignment`.
