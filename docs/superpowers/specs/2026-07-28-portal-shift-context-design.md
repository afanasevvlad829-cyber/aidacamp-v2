# Глобальный контекст смены в портале + учёт призов по сменам — Дизайн

**Дата:** 2026-07-28
**Статус:** Approved
**Область:** единый переключатель смены в шапке портала вместо разрозненного резолвинга на каждой странице; учёт, в какую смену выдан приз (без разделения остатка).

---

## Цель и объём

Портал уже разделяет часть данных по `shift_id` (`shift_event`, `room_assignment`), но каждая страница резолвит «текущую смену» по-своему или вообще не даёт переключиться на архивную. Владелец хочет единую точку выбора смены — сверху, один раз — и чтобы все смено-зависимые разделы (расселение, призы, план и что появится дальше) читали её оттуда.

Отдельно обнаружено: остаток призов (`portal_prize_custom.qty`) — общий и **переходящий** пул (не сбрасывается между сменами, продолжает убывать) — это устраивает владельца как есть. Реальный пробел не в остатке, а в том, что нельзя посмотреть, **сколько выдано именно в конкретную смену** (нет `shift_id` в журнале выдач).

**В этом спеке:**
- Глобальный свитчер смены в `PortalLayout.astro`, резолвинг в middleware, cookie-персист
- `/portal/rooms` переходит на чтение общего контекста вместо своего `getActiveShift() ?? getLatestShift()`
- `shift_id` в `portal_prize_issuance` — для отчётности «выдано в смену N»

**Не в этом спеке:**
- Разделение остатка приза по сменам — сознательно не делаем, остаток общий и переходящий, это устраивает как есть
- Сброс/пересев остатков при создании новой смены — не нужен, раз остаток не делится
- Перевод `/portal/smena`/`/portal/den` на общий контекст — их текущий механизм резолвинга смены не проверялся в рамках этого спека, выравнивание с общим контекстом — отдельная задача при реализации, если понадобится

## Архитектура

### Резолвинг смены — в middleware

`src/middleware.ts` уже кладёт `portalRole`/`portalName` в `Astro.locals` — туда же добавляется `currentShiftId`:

```
cookie 'portal_active_shift_id' есть и валиден → используем его
  иначе → getActiveShift() (shift.status='active')
    иначе → getLatestShift()
      иначе → null (нет ни одной смены)
```

Результат кладётся в `Astro.locals.currentShiftId` — читается любой страницей так же, как сейчас читается `Astro.locals.portalRole`.

### Свитчер — в `PortalLayout.astro`

Выпадающий список рядом с блоком роли в шапке (тот же ряд, где сейчас бейдж «Вы вошли как…»). Источник списка — уже существующий `listShifts()` из `portalShift.ts` (активная смена — сверху/выделена, архивные — ниже). Выбор — обычный `<select>` с `onchange`, отправляет `POST` (или просто `GET` со `Set-Cookie` через маленький API-роут `/api/portal/shift-context`), пишет `portal_active_shift_id`, дальше `location.reload()`.

### `/portal/rooms` — убрать локальный резолвинг

`const shift = await getActiveShift() ?? await getLatestShift();` (`src/pages/portal/rooms.astro:34`) заменяется на чтение `Astro.locals.currentShiftId` → `getShiftById(id)` (небольшая новая функция в `portalShift.ts`, либо переиспользование уже существующей, если такая есть). Так страница автоматически подчиняется общему свитчеру, включая просмотр архивной смены — то, чего сейчас там вообще нет.

## Данные

### `portal_prize_issuance` — добавить `shift_id`

```sql
ALTER TABLE portal_prize_issuance ADD COLUMN IF NOT EXISTS shift_id BIGINT REFERENCES shift(id);
```

При выдаче приза (`/api/portal/prize-ops`, `issueQty`/аналогичная функция в `portalPrizeOps.ts`) — берём `shift_id` из `Astro.locals.currentShiftId` текущего запроса, а не глобально. Старые записи (до колонки) остаются `NULL` — не бэкафилим задним числом, реальных данных о том, в какую смену они выданы, всё равно нет.

`portal_prize_custom.qty` **не трогаем** — общий переходящий остаток, как и был.

## Обработка ошибок

- Нет ни одной смены в `shift` (`currentShiftId = null`) → свитчер показывает «Смен нет», страницы вроде `/portal/rooms` показывают пустое состояние (как сейчас, когда `shift` = null).
- Cookie указывает на удалённую/несуществующую смену → откат на `getActiveShift() ?? getLatestShift()`, как будто cookie не было.

## Тестирование

- Юнит-тест резолвинга: cookie валиден / невалиден / отсутствует → три ожидаемых исхода.
- Ручной smoke-тест: переключить смену в шапке на `/portal/rooms` → видно данные другой смены; выдать приз на разных сменах → в журнале разные `shift_id`, `portal_prize_custom.qty` уменьшается один раз (не по разу на смену).

## Открытые вопросы для плана реализации (не блокируют дизайн)

1. Текущий механизм резолвинга смены на `/portal/smena` и `/portal/den` не проверялся — при реализации свериться, не сломает ли переход на общий `Astro.locals.currentShiftId` их существующее поведение (например, если они завязаны на URL-параметр, а не на «текущую» смену).
2. Название и точный контракт API-роута для смены cookie (`/api/portal/shift-context` или похожий) — не спроектирован в деталях, обычный небольшой POST-эндпоинт.
