# Telegram-сборщик черновиков для родительского канала — Дизайн (Фаза 1)

**Дата:** 2026-07-28
**Статус:** Approved
**Область:** сбор черновиков (текст+фото+видео) от вожатых/преподавателей через `@Aidacamp2026bot`, ручное одобрение руководителем смены, публикация в TG-канал смены.

---

## Цель и объём

Вожатые и преподаватели уже документируют смену (фото/видео/комментарии), но материал уходит родителям без единой точки контроля качества и без гарантии, что медиа не пережато. Нужен сборщик: вожатый шлёт боту сырой черновик → руководитель смены проверяет/правит/пересобирает состав → одобренное публикуется в родительский TG-канал.

**В Фазе 1:**
- Сборщик черновика (текст + фото/видео в оригинальном качестве)
- Ручное одобрение/отклонение/правка руководителем внутри Telegram
- Публикация в существующий TG-канал смены

**Не в Фазе 1** (отдельные спеки позже):
- ИИ-подписи и распознавание лиц на фото
- Привязка черновика к конкретному событию/чек-листу сетки смены (см. нереализованную концепцию в `SHIFT_TEMPLATES.md`/`UI_CONCEPT.md` — сознательно не связываем с ней в этой фазе)
- Редактирование состава медиа автором-вожатым (только руководитель на этапе одобрения)
- Авто-эскалация зависших на ревью черновиков

---

## Архитектура

Реализуется **внутри сайта** (Astro/TS-бэкенд), не отдельным Python-сервисом — потому что логике нужно знать, кто пишет (`telegram_id → portal_staff`), и это уже есть в кодовой базе (`portalStaff.ts`, `telegramAuth.ts`). Деплой идёт вместе с сайтом (`dev → main`), разработка — через `agent-docker.sh` (Правило №1).

**Не веб-хук, а постоянное MTProto-соединение.** На сервере уже найден прецедент — отдельный Python-бот `shift-content-bot` (`/opt/shift-content-bot/`, для смены 5) шлёт/принимает файлы через Telethon (MTProto), что снимает ограничение обычного Bot API на скачивание файлов >20 МБ (Telethon умеет до ~2 ГБ). Решение: взять тот же принцип, но не как отдельный Python-процесс, а через **GramJS** (JS-порт Telethon, npm-пакет `telegram`) — прямо в Node-процессе Astro. `aidacamp-prod` и так уже работает как один долгоживущий Node-процесс (см. комментарий в `src/lib/db.ts` про общий `pg.Pool`), поэтому GramJS-клиент поднимается один раз при старте сервера (модуль-синглтон, как `pool` в `db.ts`) и держит соединение всё время жизни процесса, а не по одному HTTP-запросу на апдейт. `shift-content-bot` при этом не расширяется — низкое использование преподавателями делает нецелесообразным тащить его отдельную несвязанную с порталом схему (`shift_staff`/`shift_kids`/`shift_content`) дальше.

```
Вожатый/преподаватель → DM боту @Aidacamp2026bot
  → GramJS-клиент (MTProto, авторизован как бот по BOT_TOKEN), event-хендлер на новое сообщение
    → auth: telegram_id → portal_staff (роль vozhaty/teacher/rukovoditel/admin, active)
    → копит черновик (draft_post, status='collecting') до команды /готово
    → по /готово: шлёт превью руководителю смены
       (медиа-альбом + текст + нумерованный состав + inline-кнопки)
      → «Изменить текст» → бот просит новый текст → заменяет draft_post.text
      → «Убрать элемент» → кнопки с номерами → deleteMedia() → пересобрать превью
      → «Порядок» → «пришлите новый порядок номеров через запятую» → reorderMedia()
      → «Отклонить» → уведомление автору
      → «Одобрить» → публикация в TG-канал смены (sendMediaGroup/sendVideo/sendMessage)
        → тот же канал уже зеркалится в MAX через telegram-max-sync — ничего доп. не делаем
```

## Правило «оригинал»

Telegram всегда пережимает медиа на своей стороне, если оно приходит как `photo`/`video`. Единственный способ получить оригинал 1-в-1 — приём как `document`:

- `message.photo` присутствует → **отклонить**, ответить инструкцией: «Это сжатое фото. Пришлите оригинал: 📎 → Файл (в галерее отключите сжатие/иконку HD перед отправкой)».
- `message.video` (не документ) → та же отбраковка, аналогичная инструкция для видео.
- `message.document` с mime `image/*` или `video/*` → принять, скачать оригинал.
- Документ с другим mime → отклонить («поддерживаются только фото и видео»).
- Размер файла > ~300 МБ (буфер сверх регламентных 200 МБ, см. `_notes/АйДаКемп/Регламенты-портала/00 - Общий регламент.md` §4) → отклонить с понятным сообщением.

**Ограничение обычного Bot API снято архитектурно:** `api.telegram.org` не даёт скачать файл > 20 МБ через `getFile`, но мы работаем через GramJS/MTProto (см. «Архитектура» выше), а не через классический Bot API — там лимит на скачивание файлов практически отсутствует (Telethon-прецедент `shift-content-bot` уже отправляет/принимает файлы до ~2 ГБ). Отдельного локального `telegram-bot-api`-сервера (как у `telegram-max-sync`) не требуется.

Публикация в канал использует обычные `photo`/`video` (сжато Telegram-ом, но с превью и проигрыванием видео в ленте — удобно родителям). Оригиналы при этом всё равно остаются сохранёнными на сервере — для архива, будущей ИИ-доработки и синка в MAX.

## Данные

### Новая таблица `draft_post`

```sql
CREATE TABLE IF NOT EXISTS draft_post (
  id                 BIGSERIAL PRIMARY KEY,
  shift_id           BIGINT REFERENCES shift(id),
  author_telegram_id BIGINT NOT NULL,
  status             TEXT NOT NULL DEFAULT 'collecting'
                        CHECK (status IN ('collecting','pending_review','approved','rejected')),
  text               TEXT,
  reviewer_chat_id    BIGINT,
  reviewer_message_id BIGINT,
  created_at         TIMESTAMPTZ DEFAULT NOW(),
  decided_at         TIMESTAMPTZ,
  decided_by         BIGINT
);
```

### Медиа — переиспользуем `archive_photo`

Без новой таблицы: `entity_type='draft_post', entity_id=draft_post.id` поверх уже существующих `attachMedia()` / `listMedia()` / `reorderMedia()` / `deleteMedia()` из `src/lib/portalMedia.ts`. Именно эти функции дают руководителю возможность убирать/переставлять элементы черновика на этапе одобрения без нового бэкенд-кода.

### Новая колонка `shift.tg_parent_channel_id BIGINT`

Админ проставляет вручную. **Precondition** (как у `tg-collector`): бот `@Aidacamp2026bot` должен быть добавлен в целевой TG-канал смены администратором с правом публикации — иначе `sendMediaGroup`/`sendVideo` в канал вернёт ошибку.

### Ревьюер

Единственный активный `portal_staff` с `staff_key='director'` — тот же паттерн поиска руководителя, что уже используется в `src/lib/portalPenalty.ts` (`scanUnassignedEvents`), без привязки к конкретной смене.

## Границы черновика

- Черновик копится по входящим сообщениям от одного `telegram_id`, пока автор не пришлёт `/готово` (закрывает и отправляет на ревью) или `/отмена` (сбрасывает черновик).
- Незарегистрированный/неактивный `telegram_id` или роль `student` → бот вежливо отказывает, ничего не сохраняет.

## Правка на этапе одобрения

Руководитель получает превью: медиа-альбом + текстовое сообщение с нумерованным составом и inline-кнопками:

```
Черновик от Ивана (Смена 1):

<текст>

📎 Состав:
1) Фото
2) Фото
3) Видео

[✅ Одобрить и опубликовать]  [✏️ Изменить текст]
[🗑 Убрать элемент]           [🔀 Порядок]
[❌ Отклонить]
```

- **Убрать элемент** → бот присылает кнопки с номерами → тап по номеру → `deleteMedia()` → превью пересобирается заново (с новой нумерацией).
- **Порядок** → бот просит «пришлите новый порядок номеров через запятую» → ответ парсится → `reorderMedia()` → превью пересобирается.
- **Изменить текст** → бот просит новый текст → заменяет `draft_post.text` → превью пересобирается.
- **Одобрить** → публикует текущий (уже пересобранный) состав в канал смены.
- **Отклонить** → уведомляет автора, черновик получает статус `rejected`.

Редактирование состава медиа в Фазе 1 доступно **только руководителю на этапе одобрения**, не автору во время сбора.

## Обработка ошибок

- Ошибка публикации (бот не админ канала, сеть, таймаут) → черновик остаётся `pending_review`, руководителю приходит текст ошибки, кнопку «Одобрить» можно нажать повторно — статус не откатывается сам, но и не помечается `approved`, пока публикация реально не прошла.
- Зависший на ревью черновик (руководитель не отвечает) → без авто-эскалации в Фазе 1.
- Незавершённый черновик автора (начал слать, не прислал `/готово`) → без таймаута/авто-сброса в Фазе 1.

## Открытые вопросы для плана реализации (не блокируют дизайн)

1. `TG_API_ID`/`TG_API_HASH` (данные Telegram-приложения с my.telegram.org, обязательны для MTProto/GramJS отдельно от `BOT_TOKEN`) — у `shift-content-bot` они уже есть в его `.env`; уточнить, можно ли переиспользовать те же значения для `@Aidacamp2026bot`, или нужно регистрировать новое приложение.
2. Путь хранения оригиналов на сервере — уточнить актуальный prod-путь (существующий `src/pages/api/portal/media.ts` хардкодит `/var/www/aidacamp-dev/uploads/portal`, что требует проверки на соответствие текущей топологии prod/dev).
3. Жизненный цикл GramJS-сессии в Node-процессе `aidacamp-prod` — где хранить session-файл/строку между рестартами деплоя (аналог `bot.session` у `shift-content-bot`), чтобы не требовать повторной авторизации бота при каждом деплое.
