# Фото по сменам с фильтром по ребёнку (обвязка над Immich)

**Дата:** 2026-08-03
**Статус:** утверждён

## Проблема

Фото со смен лежат в Immich (`https://photos.aidacamp.ru`), один альбом «Смена N — {год}» на смену. Родителю сейчас нечем найти именно свои фото — только листать весь альбом руками. В Immich уже включено распознавание лиц и часть детей уже подписаны именами (проверено на Смене 3: 87 из ~210 детекций лиц уже привязаны к именованным людям).

## Цель

Публичная страница на смену, где родитель выбирает своего ребёнка из списка и видит только его фото. Плюс раздел «Неразобранные» — фото с нераспознанными лицами, где любой может кликнуть на лицо и подписать имя.

## Не делаем (сознательно, чтобы не раздувать)

- Никакой авторизации родителей — страница открытая, ссылка просто расшаривается (решение владельца).
- Список детей — только те, кто уже подписан в Immich. Не сверяем с ростером AlfaCRM.
- Не создаём новых людей (`POST /api/people`) с публичной страницы — только переназначение лица (`PUT /api/faces/{id}`) на уже существующего человека из списка.
- Без пагинации — отдаём весь набор фото на смену/человека одним ответом (макс. наблюдаемый размер альбома — 860 фото, это не десятки тысяч).
- Без очереди модерации тегов — применяется сразу в Immich (решение владельца), защита — только rate-limit + проверка принадлежности faceId/personId этой смене.

## Страница

`src/pages/foto/[shiftId].astro` — `shiftId` тот же id, что в `SHIFT_META` (`shift-1`, `shift-3`...). `noindex` (как в `PortalLayout`), плюс исключение `/foto/` из фильтра sitemap в `astro.config.mjs` (по образцу уже исключённого `/staff/`).

Два режима на странице:
1. Выбор ребёнка → сетка его фото.
2. Вкладка «Неразобранные» → сетка фото с рамками нераспознанных лиц → клик по лицу → выбор имени из того же списка людей → тег применяется.

## Данные: слаг смены → альбом Immich

Имя альбома `«Смена N — {год}»` собирается из `SHIFT_META` (год = `getFullYear()` от `startDate`). Альбом ищется по имени через `GET /api/albums`, результат кэшируется в памяти процесса на несколько минут.

## API-роуты (все на сервере, `IMMICH_API_KEY` не покидает бэкенд — по образцу `src/pages/api/photo.ts`)

| Роут | Что делает |
|---|---|
| `GET /api/foto/[shiftId]/people` | Список уже именованных людей в альбоме смены (имя + id + превью). Строится перебором `GET /api/assets/{id}` по всем asset id альбома — **не** через `people` в листинге альбома, это поле там всегда пустое (проверено вживую, баг/особенность API Immich). Кэш в памяти, TTL несколько минут. |
| `GET /api/foto/[shiftId]/photos?personId=` | Пересечение альбом+человек через `POST /api/search/metadata` с `albumIds`+`personIds` (проверено вживую, работает). |
| `GET /api/foto/[shiftId]/unsorted` | Фото альбома, где есть детекция лица без имени (`person: null` или `person.name === ''`) — с bounding box для рамки. Тот же перебор `GET /api/assets/{id}`, можно посчитать заодно с `people`. |
| `POST /api/foto/[shiftId]/tag` `{faceId, personId}` | `PUT /api/faces/{faceId}` с телом `{id: personId}` (схема подтверждена на проде). Перед вызовом сервер проверяет, что faceId и personId реально принадлежат данным этой смены (не даёт использовать эндпоинт как произвольный IDOR по всей базе Immich). |
| `GET /api/foto/image/[assetId]` | Проксирует байты превью/оригинала (аналог `photo.ts`). |

## Безопасность

- `tag` — rate-limit по IP, переиспользуем готовый паттерн `Map<ip, {n, reset}>` из `src/pages/api/portal/login.ts`.
- Все остальные роуты — read-only, открытые (соответствует явному решению владельца сделать страницу без авторизации).

## Инфраструктура (не код, отдельный шаг)

`IMMICH_API_KEY` сейчас есть только в `/opt/mcp/.env` — нужно продублировать в `.env` самого сайта (prod и dev), иначе бэкенд-роуты не смогут дёрнуть Immich.
