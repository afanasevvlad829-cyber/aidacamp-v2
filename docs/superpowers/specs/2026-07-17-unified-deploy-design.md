# Единый механизм выкатки и бэкапов для 4 сайтов

**Дата:** 2026-07-17
**Статус:** дизайн, согласован владельцем
**Область:** aidacamp.ru, codims.ru, icepartners.ru, vlad-a.ru (все на одном сервере 159.194.223.55)

## Зачем

Сегодня флоу веток унифицирован (push `dev` → deploy-dev → ff-промоут `dev→main` →
deploy-prod), но **как** собирается и публикуется код — разное на каждом сайте, и это
источник двух проблем:

1. **Безопасность.** На codims/icepartners/vlad-a `npm ci` + `npm run build` выполняются
   **на проде** (codims/vlad-a — под root) из смердженного кода PR. Мерж = исполнение
   произвольного кода на проде. Это блокирует любой автономный мерж: пока держится, один
   вредный PR = RCE на проде.
2. **Бэкапы/откат вразнобой.** aidacamp — `cp -a backup-*` (3 шт.) + restic; icepartners/
   vlad-a — свап `current`/`previous` (1 шаг отката); codims — отката нет (git reset +
   пересборка). Единого одновременного off-site снапшота нет; `/opt/backups` протух.

Цель: **один механизм выкатки и бэкапов на все 4 сайта** — максимально безопасный и
эффективный, с единообразным многоуровневым откатом и одновременным off-site бэкапом.
Побочно это закрывает RCE-поверхность и делает автономный PR-мерж возможным (отдельный
проект, см. «Вне области»).

## Факты (проверено 2026-07-17)

- Все 4 сайта — на одном сервере **159.194.223.55** (Beget VPS). RAM ~4.8 Gi, из свопа
  уже занято ~2.9 Gi, 2 ядра, диск часто 90%+. Сборка на проде дорога и опасна для
  прод-трафика.
- Раскладка `/var/www`: aidacamp — плоская (rsync-in-place); codims-prod — `current`+`repo`+
  `server`; icepartners-prod и vlad-a-prod — `current`+`previous`.
- Типы отдачи в переходе: memory `four_sites_serving_topology` — движение к статике Astro
  (codims переведён 17.07), но на проде ещё живут `server/` (codims) и `icepartners-api.service`.
  Механизм обязан поддержать **и статику, и SSR** одинаково.
- Бэкапы: `/opt/restic-full-backup.sh`, `/opt/restic-snapshot.sh` есть; per-deploy снапшот
  дёргается из aidacamp `deploy.sh`. Единого таймера «всё сразу» нет.
- Реестр эталона: aidacamp `deploy.yml` уже собирает на раннере и rsync'ит `dist` — это
  безопасная модель, берём за базу.

## Архитектура: «сборка вне прода → артефакт → атомарный свап»

Одна модель, собранная из лучших частей существующего: сборка off-prod (aidacamp) +
атомарный свап (icepartners/vlad-a), углублённый до N релизов.

### 1. Сборка — только на GitHub-раннере

`npm ci && npm run build` выполняется на раннере. На прод едет **готовый `dist`**.
Исходники PR на проде не исполняются никогда. Сборка уходит с перегруженного сервера.

### 2. Публикация — версионированные релизы + атомарный симлинк

Единая раскладка на проде для всех 4 сайтов (dev и prod):

```
/var/www/<site>/
  releases/<sha>/          # rsync'нутый dist сюда (client/ [+ server/ для SSR])
  current  -> releases/<sha>
  previous -> releases/<sha-prev>
  shared/                  # .env, node_modules, данные, что переживает релизы (симлинками в release)
```

- **Выкат:** rsync нового `dist` в `releases/<sha>` → атомарный флип `current`
  (`ln -sfn releases/<sha> current.tmp && mv -T current.tmp current`) → `systemctl reload`
  для SSR / ничего для статики (nginx root = `current/client`) → smoke.
- **Откат:** флип `current` на `previous` + reload. Без пересборки, мгновенно.
- **Хранение:** последние **5 релизов**, старше — `rm -rf`. Даёт откат на 5 шагов назад,
  единообразно (сейчас 3/1/1/0).
- **Статика vs SSR:** статика — nginx `root` указывает на `current/client`, релиз меняет
  цель симлинка, nginx подхватывает без рестарта. SSR — systemd-юнит `ExecStart` использует
  `current/server/entry.mjs`, релиз + `systemctl reload/restart <service>`.

### 3. Runtime-зависимости (SSR-сайты)

`node_modules` живёт в `shared/` (переживает релизы, симлинкуется в `current`). Обновляется
на проде **только когда изменился `package-lock.json`** (сверка хеша, как в текущем aidacamp
`deploy.sh`) командой:

```
npm ci --omit=dev --ignore-scripts --prefer-offline
```

`--ignore-scripts` блокирует postinstall-скрипты зависимостей → закрывает остаточный
RCE через lockfile. Требование: зависимости проекта не должны полагаться на postinstall
(проверить на этапе внедрения; для Astro-стека это норма).

Для чисто статических сайтов `node_modules` на проде не нужен вовсе — шаг пропускается.

### 4. Единый флоу веток — без изменений

`push dev → deploy-dev(+smoke) → ff-промоут main←dev → deploy-prod(+smoke+авто-откат)`,
`concurrency` без прерывания. Меняем только тело шагов deploy-dev/deploy-prod, не структуру.

## Единый источник логики: репозиторий `deploy-ci`

Вся тяжёлая логика — в одном месте, сайты только параметризуют.

- Новый репозиторий **`deploy-ci`** (под `afanasevvlad829-cyber`) содержит:
  - `release.sh` — весь релиз-механизм (rsync в `releases/<sha>`, атомарный флип, чистка до
    5, условный `npm ci --ignore-scripts`, reload сервиса, вызов smoke, авто-откат при
    красном smoke).
  - reusable workflow `.github/workflows/deploy.yml` (`on: workflow_call`) с входами:
    `site`, `server_paths`, `service` (пусто = статика), `smoke_urls`, `build_cmd`.
- `deploy.yml` каждого сайта ужимается до ~15 строк: `uses: afanasevvlad829-cyber/deploy-ci/
  .github/workflows/deploy.yml@main` + `with:` его параметры + `secrets: inherit`.
- **Доступ на Free-приватных репо:** reusable workflow из приватного репо требует включить
  доступ в Settings → Actions → «Accessible from repositories owned by the user». Настроить
  один раз на `deploy-ci`. Если доступ окажется недоступен на текущем плане — фолбэк:
  `release.sh` синхронизируется во все 4 репо + статический гард `check:deploy-drift`
  (сверка контрольной суммы с каноном) роняет CI при расхождении. Основной путь — reusable.

Правишь механизм в одном месте (`deploy-ci`) — чинится у всех четырёх.

## Бэкапы — единые и одновременные

Два слоя, оба — один механизм на всех 4 сайтах.

### Слой 1 — быстрый откат (делает сам деплой)

`releases/` + симлинки `current`/`previous`, 5 в глубину. Заменяет разнобой
(`cp -a backup-*` / `previous` / ничего) на одну форму. Мгновенный откат без сети и пересборки.

### Слой 2 — off-site point-in-time (один таймер на всё)

Один скрипт `/opt/backup-all.sh` на **одном** systemd-таймере снапшотит за один прогон:
- `current` всех 4 сайтов (prod);
- данные, не лежащие в git: `leads/`, `clicks/`, дампы PostgreSQL, `.env`-файлы;
- в restic-репозиторий на Я.Диск (нативный rclone yandex backend, как в
  memory `project_restic_offsite_backups`).

Единый прогон = **единый момент консистентности** для всех сайтов. Заменяет разрозненные
`/opt/restic-*.sh` и per-deploy снапшоты. Медиа (`aidacamp-media`, галереи) — отдельным
restic-профилем/расписанием (крупные, отдельное хранилище по CLAUDE.md), в этот таймер не тянем.

- Ретенция restic: `--keep-daily 7 --keep-weekly 4 --keep-monthly 6` (форгет+prune в том же
  скрипте).
- Дедлайн диска: перед снапшотом проверка `df` порога; при переполнении — алерт, не тихий
  провал.

## Наблюдаемость (уроки прошлых «бутафорских защит»)

- **Смоук — источник правды выката.** Красный smoke на dev → прод не едет; красный smoke на
  проде → авто-откат на `previous`. Как в текущем aidacamp, распространяем на всех.
- **Уведомление в Telegram** об исходе каждого prod-деплоя и каждого авто-отката (шаг уже есть
  в aidacamp `deploy.yml`, вносим в reusable).
- **Heartbeat бэкапа:** `backup-all.sh` пишет файл-маркер с временем успеха; отдельный
  дешёвый чек (в существующий `health-monitor.sh`) алертит, если последний успех старше
  суток — «тишина» не должна быть неотличима от «всё ок».
- **Валидность workflow** уже проверяется в `quality-gate.yml` (урок guard-agent-prs.yml) —
  сохраняем на всех репо.

## План внедрения (порядок, безопасный откат на каждом шаге)

1. **`deploy-ci`:** создать репо, написать `release.sh` + reusable workflow, покрыть
   `release.sh` тестом на bats/shell (атомарность флипа, чистка до 5, откат при красном smoke).
2. **Пилот — vlad-a** (наименьший риск: уже `current`/`previous`, нет клиентов-школ). Migrate
   раскладку к `releases/`, перевести `deploy.yml` на reusable, сборка на раннере. Прогнать
   dev→prod, проверить откат вручную.
3. **icepartners** → **codims** (у codims доп.шаг: увести сборку с прода, снять `repo/`-build).
4. **aidacamp** последним (эталон, больше всего трафика): плоскую раскладку → `releases/`.
5. **Бэкапы:** `/opt/backup-all.sh` + один таймер, ретенция, heartbeat. Вывести из строя
   старые разрозненные restic-скрипты и per-deploy снапшот из `deploy.sh`.
6. Обновить `INFRA.md`, `DEV_PROTOCOL.md`, CLAUDE.md-карты по всем 4 репо: новая раскладка,
   единый механизм, где чинить.

Каждый шаг обратим: старый `deploy.yml` сохраняется до зелёного прогона нового; миграция
раскладки не удаляет старую `current`, пока новый релиз не прошёл smoke.

## Критерии успеха

- Все 4 сайта выкатываются одним reusable workflow; правка механизма — в одном репо.
- Сборка нигде не выполняется на проде; исходники PR на проде не исполняются.
- Откат на всех 4 — атомарный флип симлинка, ≥3 шага истории (цель 5).
- Один таймер делает консистентный off-site снапшот всех 4 сайтов + данных; есть heartbeat.
- Красный smoke останавливает прод / откатывает; исход уходит в Telegram.

## Вне области (отдельные проекты)

- **Автономный PR-ревью/мерж** — этот дизайн лишь снимает его блокер (RCE на проде).
  Сам ревью-слой (кто аппрувит, blocklist вне репо, вердикт-из-артефакта, эскалация опасных
  путей) проектируется отдельно после унификации деплоя.
- **Ротация/скоуп деплой-ключей и разнесение личностей** (merge-токен отдельно от прод-root) —
  смежная тема безопасности, не входит в эту унификацию.
- **Миграция всех сайтов в один тип отдачи** (статика vs SSR) — не требуется; механизм
  поддерживает оба.
