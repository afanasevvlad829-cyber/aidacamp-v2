## Объём

**В этом спеке:**
- Прогон каждого фото черновика (Фазы 1) через распознавание лиц Immich
- Сопоставление найденных лиц с `room_assignment.immich_person_id` → список распознанных имён на фото
- Хранение результата, доступное для спека 4

**Не в этом спеке:**
- Видео — распознавание лиц не запускаем (ML-джоба Immich заточена под фото, на видео ненадёжна); видео просто собираются как есть, без списка имён
- Ручная коррекция ошибочно распознанных имён — не проектируем: при низкой уверенности имя просто не показывается (см. «Порог уверенности»), а руководитель и так может поправить текст поста на этапе ревью (Фаза 1)
- Куда именно эти имена подставляются в текст — это спек 4, здесь только то, что данные становятся доступны

## Хранилище черновиковых фото в Immich

Черновиковые фото грузятся в **отдельный служебный альбом/тег «Черновики»** в Immich — не в курируемые «Смена N — YYYY», чтобы не засорять владельцу архив неодобренным/отклонённым материалом. Курируемые альбомы остаются ручной витриной, как сейчас.

---

## Поток на одно фото

1. Фото черновика (Фаза 1, `message.document` с mime `image/*`) сохраняется через `attachMedia()` в `archive_photo` (`entity_type='draft_post'`).
2. Сразу после сохранения — асинхронно, не блокируя ответ боту — фото загружается в Immich (альбом «Черновики»).
3. Ждём завершения ML-джобы детекции лиц Immich (асинхронная, не мгновенная — тот же нюанс, что в онбординге).
4. Для каждого найденного лица на фото — сопоставляем его Person ID с `room_assignment.immich_person_id` **в рамках той же смены**, что и `draft_post.shift_id` (черновик уже привязан к смене в Фазе 1) — исключает случайное совпадение с ребёнком другой смены.
5. Результат — список `room_assignment_id` (→ имён) на это фото — сохраняется (см. «Данные»).

Запускается сразу по приходу каждого фото во время сбора черновика (до `/готово`), а не пачкой в момент «готово» — так результат уже готов к моменту, когда черновик уходит на ревью, и не добавляет заметной задержки в этот момент.

### Порог уверенности

Immich возвращает совпадение лица с некоторой уверенностью. Показываем распознанное имя только выше высокого порога (точное значение — подбирается в плане реализации по факту работы Immich на реальных фото). Ниже порога — лицо просто не подписывается, никакого «предположительно» или запроса на подтверждение: лучше не назвать ребёнка, чем назвать неверно.

## Данные

Новая таблица (не расширяем `archive_photo` — это общая для всего портала таблица, а распознавание лиц специфично для черновиков):

```sql
CREATE TABLE IF NOT EXISTS draft_media_face (
  id                 BIGSERIAL PRIMARY KEY,
  media_id           BIGINT NOT NULL REFERENCES archive_photo(id) ON DELETE CASCADE,
  room_assignment_id BIGINT NOT NULL REFERENCES room_assignment(id) ON DELETE CASCADE,
  confidence         NUMERIC,
  created_at         TIMESTAMPTZ DEFAULT NOW()
);
```

Одно фото может дать несколько строк (несколько детей в кадре).

## Обработка ошибок

- Immich недоступен / загрузка не удалась → фото остаётся в черновике без распознанных имён, ничего не блокирует сбор/ревью/публикацию (Фаза 1 продолжает работать как без этого спека).
- ML-джоба не завершилась к моменту `/готово` (маловероятно с учётом раннего запуска по п.4 «Поток», но возможно на больших альбомах) → спек 4 использует то, что успело распознаться на момент генерации, не ждёт.
- Лицо распознано, но соответствующего `room_assignment.immich_person_id` не нашлось (ребёнок не проходил онбординг, либо это взрослый/вожатый в кадре) → просто не попадает в список, не ошибка.

## Тестирование

- Юнит-тест сопоставления Person ID → `room_assignment_id` в рамках смены (включая случай «есть Person, но не в этой смене» → не матчим).
- Ручной smoke-тест: фото с 2 детьми, прошедшими онбординг, + 1 не прошедшим → в `draft_media_face` 2 строки, третий не появляется.
