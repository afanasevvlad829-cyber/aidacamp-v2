## Когда запускается

По `/готово` (Фаза 1), **до** того как превью уходит руководителю на ревью — то есть `draft_post.text` в момент показа руководителю уже содержит сгенерированный вариант, а не сырой текст вожатого. Генерация синхронная относительно этого шага (руководитель ждёт один вызов API, не пачку последовательных).

---

## Вход для генерации

- Фото черновика (вожатый прислал как есть — vision-вход)
- Текст вожатого, если был («Дети устали, но всё зашло») — сырьё/якорь для тона, не выбрасывается
- Распознанные имена из спека 2 (`draft_media_face` → `room_assignment.kid_name`, только для медиа этого черновика)
- Контекст дня из спека 3 (`event_title`, `event_activity_type`, `menu_photo_url` — если есть, тоже как vision-вход)
- Голос: system-промпт строится на основе `_notes/АйДаКемп/DARYA_TONE_OF_VOICE.md` (уже существующий обучающий документ голоса Дарьи — используется как есть, не переписывается заново)

### Жёсткое ограничение промпта — не выдумывать имена

Модель получает **только** список имён из спека 2 и явную инструкцию: не называть по имени никого, кто не в этом списке, даже если модели «кажется», что она узнаёт кого-то на фото по описанию/контексту. Причина — Grok не инструмент точного распознавания лиц (см. спек онбординга/face-match), а собственное угадывание по фото сведёт на нет весь порог уверенности, выстроенный в спеке 2.

### Бренд-гигиена

Тот же набор ограничений, что действует для остального контента сайта (см. корневой `CLAUDE.md`): без слов `единиц`/`баллы` (→`рубл-`), без назойливого повтора «дети»/«ребёнок», без нравоучительного тона. Задаётся промптом; отдельный пост-фактум regex-фильтр не проектируем — объём текста (один короткий пост) не оправдывает отдельный конвейер проверки, руководитель и так видит текст перед публикацией.

## Модель и отказоустойчивость

- **Основная:** Grok (xAI), режим повышенной живости/юмора — по образцу `PRIMARY_MODEL`/`FALLBACK_MODEL` в `src/pages/api/ask.ts` (уже есть паттерн первичная/запасная модель в этой кодовой базе).
- **Фолбэк при ошибке/недоступности Grok:** не блокируем черновик — в `draft_post.text` идёт как есть исходный текст вожатого (пустая строка, если он ничего не писал). Руководитель может дописать текст вручную через уже существующую «Изменить текст» (Фаза 1) — генерация ИИ такая же необязательная надстройка, как и всё остальное в Фазе 2.

### Кнопка «Перегенерировать»

В превью руководителя (Фаза 1) добавляется шестая кнопка рядом с «Изменить текст»/«Убрать элемент»/«Порядок»/«Одобрить»/«Отклонить»:

```
[🔄 Перегенерировать]
```

Повторный вызов генерации с тем же входом (юмор — вещь на любителя, не каждая шутка попадёт с первого раза). Результат просто перезаписывает `draft_post.text`, превью пересобирается — использует тот же механизм пересборки превью, что уже есть в Фазе 1 для остальных кнопок.

## Данные

Новых таблиц не требуется — результат генерации просто пишется в уже существующее поле `draft_post.text` (Фаза 1). Отдельный лог версий текста (что было до перегенерации) не ведём — не запрошено, YAGNI.

## Обработка ошибок

- Grok недоступен / таймаут / нет ключа → фолбэк на исходный текст вожатого (см. выше), ничего не падает.
- Модель вернула пустой/бессмысленный текст → тот же фолбэк на исходный текст вожатого (простая проверка на пустую строку после trim).
- Распознанных имён нет (спек 2 ничего не нашёл) → генерация просто не упоминает имён, описывает сцену обобщённо — это нормальный, а не ошибочный случай.

## Тестирование

- Юнит-тест сборки промпта: корректная подстановка имён/контекста/пустых полей (все комбинации: есть имена+нет меню, нет имён+есть меню, ничего нет).
- Ручной smoke-тест на dev-боте: полный цикл с реальным фото → сгенерированный текст → «Перегенерировать» даёт другой вариант → «Одобрить» публикует именно текущий (не исходный) текст.

## Открытые вопросы для плана реализации (не блокируют дизайн)

1. `XAI_API_KEY` — новый секрет, которого пока нет ни в одном `.env` проекта (в отличие от `ANTHROPIC_API_KEY`, который уже есть) — завести и задокументировать по образцу существующих ключей.
2. Точное имя параметра/режима «повышенного юмора» в API xAI (аналог consumer-фичи «Fun Mode») — не проверено, что именно доступно программному доступу к API, а не только в приложении/вебе Grok — первая задача плана реализации.
3. Лимиты на количество/размер фото как vision-вход за один вызов у Grok API — не проверено, актуально при больших альбомах (после согласования: до 5–6 волн публикаций в день, часть — большими альбомами).
