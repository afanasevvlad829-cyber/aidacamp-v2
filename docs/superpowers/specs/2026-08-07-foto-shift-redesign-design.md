# Редизайн `/foto/[shiftId]` — дорогая тёмная галерея

Дата: 2026-08-07

## Проблема

`/foto/shift-3` (и любая `/foto/<shiftId>`) сейчас — служебный минимальный интерфейс:
светлый `<select>` со списком детей, квадратная сетка превью, простой лайтбокс без
скачивания/шеринга, видео открывается голым `<video>`. Вкладка «Неразобранные»
(разметка лиц кликами) открыта любому по прямой ссылке — это админский инструмент,
случайно оказавшийся публичным.

Нужен визуально дорогой, мобильно-адаптированный интерфейс с реальными фичами
скачивания/шеринга, который выглядит на уровне Google Photos / Apple Photos, а не
служебной страницы.

## Область изменений

Затрагивает только фотогалерею смен (`/foto/*` + её API), Immich-обвязку
(`src/lib/immich.ts`) и один новый раздел в `/admin`. Остальной сайт не трогаем.

## 1. Навигация — лента аватарок вместо `<select>`

`/foto/[shiftId].astro` вместо `<select>` показывает горизонтальную прокручиваемую
ленту круглых аватарок: первая карточка — «Все фото смены» (иконка `collection`),
дальше — по одной аватарке на каждого распознанного в альбоме ребёнка, подпись —
имя. Активная карточка подсвечена оранжевой рамкой (`--orange-500`). Клик грузит
сетку так же, как раньше грузил `loadPersonPhotos`/`loadUnsorted` (без «Неразобранные»
— см. раздел 5).

Технически — тот же `GET /api/foto/:shiftId/people` для списка, без изменений
контракта.

## 2. Умные аватарки — сервер вырезает лицо, а не берёт случайный кадр Immich

**Проблема источника:** Immich сам выбирает превью персоны (`/api/people/{id}/thumbnail`)
и делает это не всегда удачно — иногда берёт дальний/размытый кадр. Вместо доверия
Immich выбираем сами: среди всех появлений ребёнка в альбоме этой смены берём кадр,
где face-bounding-box занимает наибольшую площадь относительно всего кадра (= самый
крупный, чёткий, близкий портрет), и вырезаем квадрат вокруг него сами.

**`src/lib/immich.ts` — изменения:**
- `NamedPerson.assetIds` меняет тип с `{ id, type }[]` на `{ id, type, box: FaceBox }[]`
  — `getAlbumFaceIndex()` уже проходит по всем `RawFace` и знает box каждого
  распознанного лица; сейчас box просто не сохраняется в `peopleMap`, только в
  `groupsMap` (unsorted). Добавить его и туда.
- Новая функция `getBestFaceForPerson(person: NamedPerson): { assetId: string; box: FaceBox } | null`
  — по всем appearances считает `area = (x2-x1)*(y2-y1) / (width*height)`, возвращает
  appearance с максимальным `area`. `null` только если `assetIds` пуст (не бывает
  в норме, но на всякий случай).

**Новый эндпоинт `GET /api/foto/[shiftId]/avatar/[personId].ts`:**
- `getAlbumIdForShift` → `getAlbumFaceIndex` → находит `NamedPerson` → `getBestFaceForPerson`.
- Тянет `?kind=thumb` (preview-размер, этого достаточно для 200px аватарки) из
  `/api/foto/image/[id].ts`-логики напрямую с Immich (тот же `fetchWithTimeout` +
  `IMMICH_API_KEY`, по образцу существующего `image/[id].ts`).
- Через `sharp` (уже в зависимостях, `package.json`): вычисляет квадрат вокруг
  `box` с отступом ×2.2 от размера большей стороны лица (чтобы влезли волосы/плечи,
  не только глаза-нос-рот), клампит в границы изображения, `.extract()` +
  `.resize(200, 200)` + `.jpeg({ quality: 82 })`.
- Если `extract` падает (box вне границ, битые данные) — фолбэк на обычный
  `?kind=thumb` без кропа (та же логика, что сейчас, просто квадратом по центру).
- `Cache-Control: public, max-age=21600` (6 часов — лица не переразмечаются часто,
  но и не «навсегда», чтобы правки в admin/gallery-tagging рано или поздно дошли).

Компонент на странице: `<img src="/api/foto/{shiftId}/avatar/{personId}">` — никакой
клиентской логики позиционирования не нужно, кроп уже готовый.

## 3. Тёмная галерея — визуальный стиль

Фон `#0d1a2b` (navy-950, как `/p/[lid]` и hero-секции сайта). Сетка — CSS
`columns: 2` (mobile) / `columns: 3-4` (desktop) вместо строгого grid, чтобы разные
пропорции кадров не резались в квадрат — так выглядят премиальные фотогалереи, а не
каталог. `border-radius: 14px` на превью, `gap` через `margin-bottom` (стандартный
приём для CSS columns masonry). Тонкие оранжевые (`--orange-500` / `--orange-400`)
акценты только на активных элементах (выбранная аватарка, кнопки в лайтбоксе,
прогресс/счётчик выбора) — фото остаются главным источником цвета, никаких
дополнительных градиентов/orb-декораций поверх сетки (см. DESIGN_SYSTEM.md принцип
«photo emotion > graphic effects»).

Лайтбокс остаётся почти тем же по механике (текущий `#foto-lightbox` с prev/next/close,
свайпами, `Escape`/стрелками) — дорабатывается кнопками «Скачать» и «Поделиться»
(см. раздел 4) и футером с именем/датой, если есть.

## 4. Скачивание и шеринг

**Одно фото/видео — в лайтбоксе:**
- Кнопка «Скачать» — ссылка на `/api/foto/image/[id].ts?kind=original&download=1`.
  Эндпоинт дорабатывается: при `download=1` добавляет
  `Content-Disposition: attachment; filename="foto-{id}.jpg"` (или `.mp4` для видео —
  расширение берём из `Content-Type`, который уже проксируется из Immich).
- Кнопка «Поделиться» — Web Share API: `fetch` картинки/видео как blob →
  `new File([blob], filename, {type})` → если `navigator.canShare?.({files:[file]})`,
  `navigator.share({files:[file]})` — открывает системный шер (WhatsApp/Telegram/
  AirDrop получают сам файл). Фолбэк (Safari без поддержки files, десктоп без Web
  Share): `navigator.share({url: location.href})`, если и этого нет —
  `navigator.clipboard.writeText(location.href)` + тост «Ссылка скопирована».

**Несколько — режим выбора:**
- Долгий тап/клик по превью в сетке включает режим выбора (чекбоксы поверх
  превью, как обычно у фотогалерей). Внизу — плавающая панель
  «Выбрано: N» с двумя кнопками: «Скачать ZIP» и «Поделиться» (Web Share
  поддерживает массив `files` — там, где поддерживается, шерится сразу несколько).
- «Скачать ZIP» → `POST /api/foto/[shiftId]/zip.ts` с телом `{ ids: string[] }`
  (id из уже загруженного списка assetIds текущей вкладки — сервер не доверяет
  клиенту произвольные id, см. ниже).
- На карточке «Все фото ребёнка» / «Все фото смены» — кнопка «Скачать всё
  (N фото)», тот же эндпоинт с полным списком текущей вкладки.

**Новый эндпоинт `POST /api/foto/[shiftId]/zip.ts`:**
- Тело: `{ ids: string[] }`, максимум 300 id за раз (защита от злоупотребления/
  таймаута — если понадобится больше, фронт бьёт на несколько запросов; такое
  на практике не встретится — в смене не тысячи фото на одного ребёнка).
- **Валидация id по альбому**: сервер запрашивает `GET /api/albums/{albumId}` у
  Immich (тот же вызов, что уже делает `getAlbumFaceIndex()` внутри себя — без
  построения полного face-индекса, он тут не нужен) и оставляет только те id из
  тела запроса, что реально входят в `assets` альбома этой смены — так же, как
  `canTag()` в `immich.ts` не даёт затегать чужого человека, здесь не даём
  скачать чужой альбом по подобранному id.
- Стримит `archiver` (zip, `store`-без сжатия — фото/видео и так сжаты, экономим
  CPU) прямо в `Response` — на каждый id проксирует `original` bytes с Immich как
  поток через `archive.append(stream, { name })`, без буферизации в память
  целиком. `Content-Disposition: attachment; filename="{shiftName}.zip"`.
- **Новая зависимость** `archiver` (пакета для zip-стриминга сейчас в проекте нет)
  — добавляется в `package.json`, `npm install` перед деплоем.

## 5. Разметка лиц уходит в `/admin`

Текущая вкладка «Неразобранные» (клик по лицу → выбор из списка детей → PUT
`/api/foto/[shiftId]/unsorted`) убирается с публичной `/foto/[shiftId]` целиком —
случайный человек по прямой ссылке не должен иметь возможность подписать чужого
ребёнка.

Переезжает в новую `src/pages/admin/gallery-tagging/[shiftId].astro`, за тем же
гейтом, что `/admin/p-link.astro` (`ADMIN_KEY` — `?key=` или заголовок
`x-admin-key`). Внутри — тот же UI и та же логика, что сейчас в блоке
«Неразобранные» (позиционирование меток по `FaceBox`, список выборов, PUT на
`/api/foto/[shiftId]/unsorted`) — эндпоинты `people.ts`/`unsorted.ts` не меняются,
меняется только то, откуда их дёргают.

## 6. Память выбора — cookie

`document.cookie` (не localStorage — так просил владелец): `foto_person_{shiftId}=
{personId}`, `path=/foto/{shiftId}`, `max-age=15552000` (180 дней — весь сезон
смен). При заходе на страницу, если кука есть и `personId` всё ещё присутствует в
свежем списке `people` — сразу открывается его лента (без обязательного клика по
аватарке). Кука перезаписывается при каждом ручном переключении на другого
ребёнка/«Все фото».

## 7. Обогащение CRM — Яндекс ClientID и прочее

По аналогии с `/p/[lid].astro` (та же механика, тот же `/api/bind-lead`, который
не меняется): `/foto/[shiftId]` принимает необязательные `?lid=<crm_id>&t=<hmac>`
(подпись — существующие `signLid`/`verifyLid` из `src/lib/leadLink.ts`, тот же
секрет).

Когда пара валидна — клиентский скрипт (копия паттерна `collectClientData()` +
`bindCid()` из `/p/[lid].astro`, но не in-line дублирование: выносится в общий
модуль `src/lib/attribution/collectAndBind.ts` — используется из `/foto/[shiftId]`
и из `/p/[lid]`, чтобы не плодить одну и ту же логику в двух местах) ждёт `window.ym`
(Метрика уже лениво грузится через `Base.astro`, отдельно подключать не нужно),
собирает `ym_client_id` (через `ym(96499295,'getClientID', cb)`), UTM/referrer/
screen/lang/tz/`_ym_d`/`vk_top_vid`/`ubtcuid`/`domain_userid`, шлёт `POST
/api/bind-lead` с `{ lid, t, ym_client_id, is_manager: false, ...extra }` — эндпоинт
уже умеет: пишет в `pamyatka_bindings`, дописывает строку в заметку CRM-клиента,
доливает `ymuid`/`ubtcuid`/`domainid` в кастомные поля Альфы (fill-if-empty).
`sessionStorage` ключ `foto_bound_{shiftId}_{lid}` — не слать повторно на каждый
reload той же вкладки (тот же приём, что `pm_bound_{lid}`).

Без `lid` в URL страница работает как обычно, просто не обогащает (органические
заходы по ссылке из TG-канала родителей без персонализации).

**Чтобы ссылку можно было реально выдать:** `/admin/p-link.astro` получает второе
поле — `<select>` смены (из `mainShifts`/`allShiftsIncludingArchived`,
`src/data/shifts.ts`). При выбранной смене под уже существующей ссылкой на памятку
показывается вторая ссылка: `https://aidacamp.ru/foto/{shiftId}?lid={lid}&t={signLid(lid)}`.
Один и тот же `t` (подпись зависит только от `lid`, не от `shiftId`) — переиспользуем
`signLid(lidNum)`, уже посчитанный на странице.

## Что осознанно не делаем

- Не трогаем сам Immich (не переобучаем распознавание лиц, не правим его данные) —
  только по-своему выбираем, какой уже размеченный кадр показать аватаркой.
- Не делаем полноценный auth для `/foto/[shiftId]` (как был публичным по прямой
  ссылке, так и остаётся) — это осознанное решение с самого начала фичи, редизайн
  его не меняет, кроме удаления опасной вкладки разметки.
- Не кэшируем ZIP на диске — генерируется на лету при каждом запросе (архивы
  собираются нечасто, не такая уж горячая точка, чтобы усложнять кэшем).
