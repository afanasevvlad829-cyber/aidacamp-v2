## 4. Шаблоны чек-листов (canonical)

Reusable. Привязываются к нескольким событиям через `event_checklist`. Галочки личные, по `(событие, пункт, telegram_id)`.

### `checklist.meal_dezhurny` — Дежурный на приёме пищи
1. Привела/привёл группу в столовую
2. Посчитала/посчитал детей (X из X)
3. Сфотографировала меню
4. Дети не берут по 3 порции
5. Села/сел есть последним

### `checklist.lesson_teacher` — Преподаватель на занятии
1. Материалы и слайды готовы
2. Дети расселись по местам
3. Сделал/сделала фото момента работы
4. Назначил/назначила задание на дом или повторение
5. Закрыл/закрыла занятие — прокомментировал результаты

### `checklist.lesson_vozhatyi` — Вожатый при сопровождении группы
1. Привёл/привела группу в кабинет вовремя
2. Группа в полном составе
3. Передал/передала ответственность преподавателю
4. Забрал/забрала группу после пары

### `checklist.pool_safety` — Сопровождение в бассейн
1. Все дети в плавательной форме
2. Проинструктировал по правилам
3. Все вышли — посчитал перед выходом
4. Все собрались после плавания — посчитал
5. Влажные вещи переданы для сушки

### `checklist.evening_event` — Вечернее мероприятие
1. Программа подготовлена
2. Дети собраны
3. Сделано видео и фото
4. Огонёк завершён без конфликтов
5. Дети разведены по комнатам

### `checklist.room_check_before` — Приёмка номеров (минус-первый день)
1. Все комнаты подготовлены санаторием
2. Кровати застелены, бельё свежее
3. Сантехника работает (вода, унитаз, душ) в каждой комнате
4. Свет работает (все лампы, розетки) в каждой комнате
5. Уборка проведена
6. Дефекты сфотографированы + краткое описание
7. Список комнат с распределением направлен руководителю

### `checklist.bus_loading` — Сбор у автобуса
1. Прибыл на место в 10:00, проверил список
2. Принял договор у каждого родителя
3. Выдал мерч каждому ребёнку
4. Посчитал детей перед посадкой
5. Все в автобусе — двери закрыты — отправление в 10:30

### `checklist.medical_check` — Медосмотр по приезду
1. Все справки в наличии для каждого ребёнка
2. Медик принял группу
3. Дети-исключения зафиксированы (аллергии, особенности)
4. Группа передана для расселения

### `checklist.housing_assignment` — Расселение
1. План расселения согласован
2. Каждый ребёнок знает свою комнату
3. Чемоданы донесены до комнаты
4. Дети устроились — фото комнаты
5. Список расселения отправлен руководителю

### `checklist.director_daily` — Руководитель смены (ежедневный)
1. Утренний обход территории
2. Проверка готовности команды к дню
3. В течение дня — координация и съёмка
4. Сбор фото в архив дня
5. Подготовка и публикация отчёта по дню родителям

### `checklist.test_distribution` — Тестирование и распределение по группам (день заезда)
1. Тестовое задание подготовлено
2. Каждый ребёнок прошёл тест
3. Junior / Senior — распределение зафиксировано в портале
4. Список групп отправлен вожатым

### Особенности дня заезда

1. **Сценарий знакомства в автобусе** — слот пустой, доделает методист отдельно.
2. **Распределение Junior/Senior** — фиксируется в БД в этот день; типовые дни 2+ опираются на это распределение.
3. **Уточнения по расселению по пути** — реализуется через комментарии к карточке `housing_assignment`, не отдельные события.
4. **Жёсткое расписание обеда** санатория — обед стоит в 13:00, в типовых днях это якорь, нельзя двигать.

### Правила контентного покрытия в типовом дне

- 6–8 контент-точек в день максимум
- Не каждое событие имеет контент-задачу
- Конкретные задания на конкретный день выбираются из пулов в контент-плане смены — авторская работа руководителя один раз перед сменой
- На дне с бассейном `pool.jump_video` приоритетнее остальных по визуальной силе

### Дежурство вожатых

Дежурный вожатый меняется по дням: `counselor_1` — нечётные, `counselor_2` — чётные. Сохраняется в `shift_event.assigned_staff_id`.

### Новый workflow: видео приёмки каждой комнаты

В минус-первом дне (29 мая) приёмка номеров — это **не одно общее событие с одним чек-листом**, а **процесс по комнатам**. Вожатый идёт по списку расселения (он уже подготовлен в портале) и снимает **отдельное видео для каждой комнаты**.

#### Структура UI приёмки

1. Вожатый открывает день -1 → видит карточку «Приёмка номеров»
2. Внутри карточки:
   - Прогресс-полоса «N из M комнат снято»
   - Кнопка «Зафиксировать дефект» (фото + текст) для разовых проблем
   - Кнопка «Общий чек-лист» (`checklist.room_check_before` — общая готовность санатория, не по комнатам)
   - **Список всех комнат смены** (берётся из существующей таблицы расселения)
3. У каждой комнаты:
   - Номер комнаты + список заселяющихся детей
   - Статус: `снято` (зелёная плашка + кнопка перезаписать) / `следующая` (выделена, большая кнопка «Снять видео») / `не снято` (серый вид)
4. Когда все комнаты сняты — кнопка «Завершить приёмку» активируется, событие автоматически помечается закрытым

#### Привязка медиа к комнате

Видео при загрузке через кнопку напротив комнаты привязывается к `archive_photo` с полями:

- `event_id` = ID события «Приёмка номеров» дня -1
- `room_id` = ID конкретной комнаты
- `file_type` = `video`
- `author_telegram_id` = `counselor_1` (приехал на приёмку)

#### Видео остаётся при комнате на всю смену

В админ-разделе расселения у каждой комнаты появляется блок «Медиа приёмки»: видео-плеер, дата записи, кнопка «Перезаписать». Это страховка на случай претензий от родителей или санатория — есть зафиксированное состояние номера на момент заезда.

### Двойная публикация в день защиты (день 8)

`day_report` за день 8 содержит **два блока публикации** с разными ИИ-черновиками:

1. **Парадный пост** (днём после защит и награждения) — короткий, фото с защит + дипломы, публикация в реальном времени
2. **Финальный отчёт смены** (вечером после костра) — большой пост с галереей всего вечера: маршмеллоу, сосиски, круг прощания. Это **прощальный пост смены**, который родители сохранят. Сюда же может попасть видеоролик-нарезка лучших моментов смены

В UI редактора отчёта руководитель видит **переключатель «Парадный / Финальный»** — генерируются два разных ИИ-черновика. Каждая публикация имеет отдельный `telegram_message_id`.

## 15. Архитектура JSON-seed системы

Чтобы было удобно итерировать («добавил событие — поменялась смена»), вся конфигурация смены хранится в JSON-файлах, а не в коде. БД — это только runtime-состояние: галочки, фото, отчёты.

### Структура папки seed

```
/seed/
├── shift_2026_05_30.json       — конкретная смена (события, состав)
├── shift_2026_06_10.json       — следующая смена
├── canonical/
│   ├── content_tasks.json      — пул контент-заданий (раздел 3)
│   ├── checklists.json         — шаблоны чек-листов (раздел 4)
│   └── day_templates.json      — шаблоны дней
```

### Workflow обновления

1. Руководитель открывает JSON в редакторе или в портале через `/admin/grid`
2. Меняет: переставляет ужин, добавляет событие, меняет контент-задание
3. Запускает `npm run portal:seed -- shift_2026_05_30.json`
4. Скрипт сравнивает с БД и применяет дифф — **не трогая** выставленные галочки и загруженные фото

### Принцип «JSON — конфигурация, БД — состояние»

| Хранится в JSON | Хранится в БД |
|---|---|
| Расписание событий | Галочки в чек-листах |
| Шаблоны чек-листов | Загруженные фото и видео |
| Контент-задания (пул) | Статус выполнения контент-заданий |
| Назначения ответственных | Опубликованные отчёты с TG message_id |
| Шаблоны дней | Сессии входа в портал |

Из этого следует: руководитель может **переименовать событие или добавить пункт в чек-лист** в JSON и переимпортировать — старые галочки за это событие сохранятся, новый пункт появится незаполненным.

### Идемпотентность импорта

Импорт-скрипт:

- Использует **семантические ID** из JSON (`ev-d1-01-bus-loading`) как `external_id` в БД
- Никогда не удаляет физически — помечает `is_deleted = true`
- При повторном импорте с тем же ID — апдейтит запись
- Если событие удалили из JSON, а в БД есть привязанные фото — событие помечается удалённым, но не стирается

### Скрипт импорта

`scripts/portal/seed.ts` — Node.js скрипт, принимает путь к JSON, читает, сравнивает через Drizzle ORM, применяет транзакционно. Логирует в `seed_log` для audit trail.

Безопасный режим: `npm run portal:seed:dry-run -- shift_2026_05_30.json` — выведет diff без применения.

### Тестовый прогон до старта смены

За 2 дня до 30 мая — **боевой прогон**: создаётся фейковый «день -2» с одним событием «Проверка портала», все 5 человек заходят с телефонов, ставят галочку, загружают фото, руководитель пишет тестовый отчёт. Если проходит — стартуем. Если нет — ловим баги в пятницу 28-го.

### Критичные риски

1. **Telegram WebApp + видео** — на iOS до 16.4 могут быть проблемы с большими файлами. Тестировать на устройствах команды
2. **Расписание санатория Изумруд** — питание в 13:00 жёсткое, расхождение с реальностью санатория ломает шахматку. Финальное согласование до **28 мая**
3. **TG-бот в канале родителей** — у бота должны быть права администратора. Проверить до старта
4. **Имена сотрудников** — без них seed не залить с реальными `telegram_id`. Получить от руководителя до **28 мая**
