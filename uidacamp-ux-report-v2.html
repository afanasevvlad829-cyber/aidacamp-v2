P1 — Критичные проблемы 5
P1
Hero-форма скрыта по умолчанию на мобилке — главный CTA недоступен без скролла

src/components/hero/Mobile.astro, блок #hero-booking-block — max-height:0; opacity:0; pointer-events:none по умолчанию. Форма появляется только после 30 секунд или тапа.

Первый экран мобилки не содержит кликабельного CTA для сбора лида. Trust-блок и статистика присутствуют, но нет явного призыва к действию, ведущего к форме. Кнопка «от 48 000 за 7 дней» открывает ShiftModal, а не форму — пользователь не понимает следующего шага. Правило Fitts's Law: самое важное действие должно быть доступно без дополнительных шагов.

Добавить видимую кнопку «Получить консультацию» или «Узнать цены» прямо на герое под trust-блоком (до fold). Стиль: rounded-[12px] bg-orange-500 px-6 py-3.5 text-[15px] font-semibold text-white w-full. Тап по ней разворачивает форму (анимация уже готова). Не трогать саму форму — менять только точку входа.

Правило: Primary CTA must be visible above the fold on mobile — Nielsen Norman Group; Fitts's Law.

P1
LCP 3.2 с на мобилке — Hero-изображение загружается без явного preload

src/components/hero/Mobile.astro — изображение помечено loading="eager" fetchpriority="high", но <link rel="preload"> в <head> для AVIF/WebP не добавлен. Lighthouse LCP = 3.2 с (порог хорошего: < 2.5 с).

LCP 3.2 с — в жёлтой зоне (норма до 2.5 с). Это напрямую влияет на CWV и позиции в поиске. На медленных соединениях (3G) реальный пользователь видит пустой тёмный экран 4–5 секунд — это откажет до ~20% мобильных посетителей.

В src/layouts/Base.astro (или аналогичном layout) добавить в <head>:
<link rel="preload" as="image" type="image/avif" href="/images/hero-mobile.avif" media="(max-width: 767px)">
Для десктопа отдельный preload с media="(min-width: 768px)". Это сократит LCP на 0.5–0.8 с по данным аналогичных сайтов.

Правило: LCP image should be preloaded — Google Core Web Vitals; Web.dev.

P1
TBT 220 мс — UI блокируется на 220 мс, клики не реагируют при загрузке

Lighthouse TBT (Total Blocking Time) = 220 мс. Основной источник — JavaScript-скрипты инициализации (initPhoneInput, initBookingBar, initStickyCta, UTM-fetch) выполняются в main thread.

TBT > 200 мс — жёлтая зона (норма до 150 мс). На мобильных устройствах среднего класса при тапе на кнопку в первые 3 секунды после загрузки тап может быть проигнорирован. Ухудшает INP (Interaction to Next Paint) — новый Core Web Vitals.

1. Перенести initStickyCta и initBookingBar в requestIdleCallback — они не нужны в первые 100 мс.
2. UTM-fetch (/api/hero-variants.json) обернуть в setTimeout(() => fetch(...), 500) — перенести за первый paint.
3. Использовать <script defer> вместо is:inline где возможно.

Правило: Minimize main thread work — Google Web Performance; TBT должен быть < 150 мс.

P1
Контраст белого текста на светло-оранжевом overlay в мобильном hero — не проходит WCAG AA

src/components/hero/Mobile.astro — Trust-бейджи «Лицензия / Медсестра / Страховка»: фон bg-[#1e40af]/40 + border border-[#60a5fa]/50, текст text-[#bfdbfe] (13px). На реальном тёмном фоне это работает, но при светлом hero-фото в верхней части и переходе контраст может упасть ниже 4.5:1.

Текст 13px полужирный на полупрозрачном синем фоне поверх фотографии — контраст зависит от подложки. Если hero-фото светлое (дети на солнце), бейджи теряют читаемость. WCAG AA требует минимум 4.5:1 для текста до 18px. Это касается 10–15% аудитории с пониженным зрением.

Добавить backdrop-blur и усилить непрозрачность: bg-[#1e3a8a]/70 backdrop-blur-sm. Текст поменять на чистый белый text-white вместо text-[#bfdbfe]. Это даёт гарантированный контраст 7:1+ независимо от фото.

Правило: WCAG 2.1 SC 1.4.3 Contrast (Minimum) — текст минимум 4.5:1.

P1
Sticky-бар появляется только после ухода героя из viewport — на коротких страницах не появляется никогда

src/components/StickyCta.astro строки 213–227 — sticky-бар показывается через IntersectionObserver когда hero уходит из viewport. На LP-страницах без секции #hero — только после scrollY > 480px.

На лендинговых страницах (SEO LP — /lager-dlya-podrostkov и т.д.) hero нет. Если контент короткий (меньше 480px скролла), sticky-бар не появляется вообще. Пользователь дочитывает страницу — звонить некуда. Это прямая потеря конверсий с SEO-трафика.

Изменить условие показа: показывать sticky-бар после первого скролла (scrollY > 100px), а не после ухода hero. На главной странице логика через IntersectionObserver правильная — там hero большой. На LP добавить if (document.body.scrollHeight < 900) showBar() сразу при DOMContentLoaded.

Правило: Persistent CTA should always be accessible — Baymard Institute Mobile UX Research.

P2 — Важные улучшения 7
P2
H1 усечён на мобилке — «7–15» без слова «лет» теряет смысл

src/components/hero/Mobile.astro строка 41–43: H1 «Летний лагерь в Подмосковье, 7–15». Слово «лет» отсутствует — обрыв из-за UTM-замены.

Пользователь видит «7–15» без контекста — что это? Цена? Время? Дата? Первые 3 секунды — критичны для удержания. Неполный заголовок повышает показатель отказов. UTM-варианты перезаписывают заголовок, но базовый текст должен быть полным.

Изменить базовый H1 на «Летний лагерь в Подмосковье — дети 7–15 лет». UTM-варианты заменяют его полностью — базовый текст должен быть самодостаточным. Аналогично для desktop H1.

Правило: Headlines must be self-sufficient without context — NNG Writing for the Web.

P2
Кнопка «Забронировать» в LeadForm disabled до заполнения телефона — нет подсказки почему

src/components/LeadForm.astro строки 83–93 — кнопка submit disabled по умолчанию, активируется только при валидном телефоне + чекбоксе согласия. Нет tooltip или текста-подсказки.

Пользователь не понимает, почему кнопка серая. Это создаёт cognitive friction. Баймард-исследование: 17% пользователей бросают форму если CTA disabled без объяснения. Особенно критично на мобилке — экран маленький, связи между полем и кнопкой не видно.

Добавить под полем телефона текст-подсказку (скрытую по умолчанию), которая появляется при тапе на disabled-кнопку: «Введите номер телефона для продолжения». Альтернатива: кнопка всегда активна, валидация при submit — тогда сфокусировать на поле с ошибкой и показать shake-анимацию.

Правило: Disabled buttons need explanation — Baymard Institute Form Usability Guidelines.

P2
BookingBar скрыт на мобилке (hidden lg:block) — inline-форма недоступна на телефоне

src/components/BookingBar.astro строка 10 — class="hidden lg:block ...". BookingBar видна только на desktop (≥1024px). На мобилке она полностью скрыта.

BookingBar — самая простая и быстрая форма (только телефон + кнопка). Именно она должна быть доступна на мобилке. При этом главная мобильная форма в hero скрыта по умолчанию (P1-1). Получается что на 70%+ трафика (мобилка) нет ни одного мгновенно доступного способа оставить заявку.

Изменить hidden lg:block на просто block, упростив мобильную версию: только заголовок + поле телефона + кнопка вертикально. Добавить md:flex-row для десктопного layout. Это создаст дополнительную точку захвата лида в середине страницы.

Правило: Lead capture should be accessible at multiple page positions — CRO best practices.

P2
footer использует <details>/<summary> с текстовым символом ▾ — не стилизован, выглядит как баг

src/components/Footer.astro строки 59–80 — мобильный footer использует native <details> с «Документы ▾», «Разделы ▾». Символ ▾ захардкожен в тексте, не переворачивается при открытии.

Нативный <details> открывается без анимации. Статический ▾ не меняется на ▴ при открытии — пользователь не знает, открыто ли. Это нарушает принцип system status visibility (Nielsen). Выглядит как незаконченный компонент по сравнению с остальным дизайном сайта.

Заменить <details> на styled accordion с bi bi-chevron-down иконкой, которая вращается на 180° через transition-transform rotate-180 при открытии. Или использовать CSS-хак: details[open] summary .icon { transform: rotate(180deg); }. Добавить анимацию через max-height transition.

Правило: System status must be visible — Nielsen's 10 Usability Heuristics #1.

P2
Карусель отзывов на мобилке — нет swipe-gesture cue, dots не кликабельны для навигации

src/components/Reviews.astro строки 24–62 — горизонтальный scroll-snap с dots. Dots (строка 54–62) — это <span> элементы без role="button" и без click-handler. Только визуальный индикатор.

Пользователь не понимает что можно свайпать — нет ни стрелки, ни peek следующей карточки (carousels должны показывать ~10% следующего элемента как affordance). Dots без клика — бесполезный UI-элемент, создающий ожидание что он работает.

1. Уменьшить min-w-[88%] до min-w-[82%] — peek 8% следующей карточки создаёт визуальный affordance свайпа.
2. Добавить к dots role="button" tabindex="0" и JavaScript-обработчик который делает scrollTo к нужной карточке.
3. Добавить aria-label="Перейти к отзыву N" для доступности.

Правило: Carousels must show peek of next item — Baymard Carousel Usability; WCAG 2.1 SC 2.1.1.

P2
Best Practices Lighthouse 77/100 — смешивание HTTP и HTTPS ресурсов

Lighthouse Best Practices 77/100. Вероятная причина — смешанный контент или устаревший JavaScript API. Точный источник требует просмотра Lighthouse детализированного отчёта через lighthouse.js --html.

77/100 в Best Practices — ниже рекомендуемых 90+. Это может включать: устаревшие JS API, console.error в production, небезопасные куки, отсутствие HSTS. Браузер может блокировать смешанный контент, что ломает часть функционала.

Запустить детальный Lighthouse HTML-отчёт: node /opt/browser-agent/lighthouse.js https://aidacamp.ru --mobile --html --output /tmp/lh.html и проверить конкретные нарушения в секции Best Practices. Первое подозрение — удалить все console.warn/error из production-скриптов или обернуть в if (import.meta.env.DEV).

Правило: Lighthouse Best Practices должен быть 90+ — Google Web Vitals Guidelines.

P2
Мобильное меню открывается без focus trap — при навигации с клавиатуры фокус уходит за меню

src/components/MobileMenu.astro — при открытии меню menu.classList.add('flex'), но нет focus trap. Не реализован inert на контент за меню. При нажатии Tab фокус уходит на элементы страницы под меню.

Нарушение WCAG 2.1 SC 2.4.3 (Focus Order) и ARIA pattern для modal dialogs. Скринридеры озвучивают контент страницы за меню. Пользователи с клавиатурой не могут нормально работать с меню. Аудит Lighthouse Accessibility 93/100 — возможно именно это и снижает оценку.

При открытии мобильного меню добавить document.querySelector('main').inert = true и выставить фокус на первый элемент меню: menu.querySelector('a')?.focus(). При закрытии — убрать inert и вернуть фокус на кнопку-бургер. Добавить Escape-закрытие: document.addEventListener('keydown', e => e.key === 'Escape' && closeMenu()).

Правило: Modal dialogs must trap focus — WCAG 2.1 SC 2.4.3; ARIA Authoring Practices Guide.

P3 — Доработки 6
P3
Размер звёзд в карточках отзывов — 12px (h-3 w-3) слишком мелкий для мобилки

src/components/Reviews.astro строка 35 — звёзды в карточках отзыва class="h-3 w-3" (12px). Заголовок секции имеет звёзды h-4 w-4 (16px).

12px звёзды на мобилке почти не видны. Это основной trust-элемент карточки — визуальный рейтинг. Мелкие звёзды снижают воспринимаемое качество отзыва. Несоответствие с 16px звёздами в заголовке — inconsistency.

Заменить h-3 w-3 на h-3.5 w-3.5 (14px) в карточках. Это минимальное изменение, которое улучшает читаемость без изломки layout.

Правило: Trust signals must be clearly visible — CRO Visual Hierarchy principles.

P3
Desktop hero H1 — w-[700px] фиксированная ширина может обрезаться на экранах 768–900px

src/components/hero/Desktop.astro строка 56 — class="w-[700px]" фиксированная ширина. Hero показывается с md:block т.е. с 768px, а при 768–800px ширина экрана может быть 768px и H1 в 700px + 64px left-padding = выходит за экран.

На планшетах 768–820px заголовок может обрезаться или переносить неправильно. Это промежуточное состояние между мобилкой и десктопом — часто игнорируется, но именно на планшетах много семейного трафика (родители выбирают лагерь).

Заменить w-[700px] на max-w-[700px] w-[calc(100vw-120px)] или на w-[min(700px,calc(100vw-80px))]. Это позволит заголовку адаптироваться на планшетах.

Правило: Fixed-width text containers are fragile — Responsive Design best practices.

P3
Desktop sticky bubble — low contrast button (text-white/70 на bg-slate-800/90)

src/components/StickyCta.astro строки 118 — desktop bubble toggle: text-white/70 (rgba белый 70%) на bg-slate-800/90. Контраст: примерно 4.2:1 — чуть ниже WCAG AA (4.5:1).

Иконка телефона в sticky-пузыре слегка бледная. Не критично, но при проверке контраст-анализатором нарушает WCAG AA. Простейшее исправление.

Заменить text-white/70 на text-white/80 — это даст контраст ~5.1:1 с bg-slate-800. Minimal change, maximum compliance.

Правило: WCAG 2.1 SC 1.4.3 — иконки-кнопки требуют 4.5:1.

P3
Age-кнопки в LeadForm — 34px высота (h-[34px]) ниже минимального tap-target 44px

src/components/LeadForm.astro строка 24 — блок с кнопками возраста h-[34px]. Кнопки «7–9 лет», «10–12 лет», «13–15 лет» — 34px в высоту.

Apple HIG и Google Material Design требуют минимальный tap-target 44px. 34px — на 22% меньше. На форме это первый шаг — выбор возраста. Промах по маленькой кнопке фрустрирует и может привести к выбору не той группы, что снижает качество лида.

Изменить h-[34px] на h-[44px] и обновить внутренний padding кнопок с py-2 на py-3. Форма немного вырастет в высоту, но это допустимо — лид важнее компактности.

Правило: Touch targets minimum 44×44px — Apple HIG; Google Material Design 3.

P3
About-секция: карточки 85vw показывают обрезанный peek — нет affordance следующей карточки

src/components/About.astro строка 32 — w-[85vw] min-w-[85vw]. На экране 375px: карточка 318px + gap 12px = peek следующей всего 45px. Аналогично в Reviews.

45px peek — это очень мало. Следующая карточка едва видна. Пользователь не понимает что есть ещё. Dots-навигация (2 маленьких кружка) дублирует информацию, но не является достаточным affordance для свайпа.

Изменить w-[85vw] min-w-[85vw] на w-[78vw] min-w-[78vw]. На 375px это даст peek 67px — достаточно чтобы было понятно. Аналогично в Reviews.astro изменить min-w-[88%] на min-w-[80%].

Правило: Carousels must show 15–20% of next item as affordance — Baymard Institute.

P3
mobile-ux-p0.css переопределяет классы через !important — потенциальный source of truth конфликт

src/styles/mobile-ux-p0.css — файл содержит множество !important правил для .text-slate-400, .text-slate-500, .bg-primary. Файл подключён глобально.

Глобальный CSS с !important — долговой технический файл. Новые компоненты с text-slate-500 автоматически получают переопределение, что может дать неожиданный цвет в несвязанных местах. Трудно дебажить. Если исправления из этого файла уже внедрены в компоненты — файл можно удалить.

Аудит: проверить какие из правил mobile-ux-p0.css уже отражены в компонентах напрямую. Перенести оставшиеся в конкретные компоненты через Tailwind-классы. Затем удалить файл. Если удалить нельзя — добавить комментарий с перечнем что ещё не перенесено и датой планируемого удаления.

Правило: Avoid !important overrides in global CSS — CSS Architecture best practices (ITCSS, BEM).

Оба H1 правильно структурированы, canonical задан, meta-description оптимальный (159 символов), структура H2 логична. Два H1 в разметке (mobile/desktop) — решение обосновано и допустимо.

Все изображения имеют явные width/height атрибуты. Нет элементов которые бы появлялись и сдвигали текст. Отличный результат — особенно для hero с фото.

Иконки через Bootstrap Icons + манифест — правильная архитектура

Подход с icons-manifest.json исключает конфликты при параллельной разработке. Отсутствие эмодзи в UI-компонентах — соответствует правилам проекта. SVG-иконки в StickyCta инлайновые — нет дополнительных HTTP-запросов.

Форма LeadForm — хорошая UX-механика age-select

Три кнопки возраста как первый шаг — снижают когнитивную нагрузку, одновременно собирают сегментационные данные. Метрика-цель age_select корректно привязана. Автозаполнение из localStorage — удобно при повторном визите.

Trust-блок в мобильном hero — правильный набор сигналов

4 числовые метрики (лет, детей, рейтинг, ТОП-4) + 3 trust-бейджа (лицензия, медсестра, страховка) — закрывают главные страхи родителей. Кликабельность к соответствующим якорям — продуманная навигация.

Performance 88/100 и FCP 1.5 с — быстрый сайт
