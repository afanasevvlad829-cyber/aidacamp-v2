# METHODOLOGY — Свод правил и методологий

Универсальный документ для передачи агенту. Без привязки к конкретному проекту, домену или аудитории.

---

## 1. SEO-методология

### 1.1 Семантика и кластеризация

- Источник ключей — всегда реальные данные (Wordstat, GSC, позиции из трекера), не гипотезы
- Каждый ключ имеет частотность (W) — без неё ключ не берём в работу
- Кластеризация по позициям: 1–10, 11–20, 21–30, 31–40, 41–50, 51+ — каждый кластер требует своей стратегии
- **Быстрые победы** — кластер 11–20: страница уже видна, нужен минимальный толчок
- **Средние** — 21–30: усиление тех же страниц что и 11–20
- **Долгосрочные** — 31–40+: высококонкурентные запросы, агрегаторы и госсайты, горизонт 6–12 месяцев
- Одна страница = один основной кластер + хвост из смежных ключей
- Приоритет кластера = суммарная частота W × близость к топу

### 1.2 Мета-теги

- **Title**: максимум 60–65 символов — Яндекс и Google обрезают длиннее
- **Description**: 150–160 символов — длиннее обрезается в сниппете, короче — недоиспользование
- Title и description должны содержать основной ключ кластера органично, без спама
- Каждая страница — уникальные title и description, без дублей по сайту
- Canonical обязателен на всех страницах, особенно при наличии UTM-параметров

### 1.3 Заголовки и структура

- H1 — один на странице, содержит основной ключ, совпадает по смыслу с title
- H2–H6 — иерархия не нарушается (не H1 → H4, пропуски недопустимы)
- H2 должны покрывать ключевые подзапросы кластера
- Alt у всех изображений — описательный, содержит ключ там где уместно, не спам

### 1.4 Технический SEO-чеклист

- [ ] Canonical URL прописан и совпадает с целевым адресом
- [ ] robots.txt не блокирует важные страницы
- [ ] Sitemap актуален, содержит все индексируемые URL
- [ ] Schema.org разметка: FAQPage, Organization, BreadcrumbList, Offer — по типу страницы
- [ ] Нет дублей страниц (с / и без /, с www и без)
- [ ] 404 страница есть и не индексируется
- [ ] Все редиректы 301, не цепочки
- [ ] Hreflang если есть языковые версии

### 1.5 Контентная оптимизация

- Объём текста — не метрика сама по себе: важна полнота раскрытия темы
- Поведенческие сигналы важнее объёма: bounce rate, scroll depth, время на странице
- Scroll depth < 30% = контент не читают = нужен редизайн первого экрана или структуры
- Bounce rate > 70% для лендинга = несоответствие интента или слабый first screen
- Quickback > 15% = страница не отвечает на запрос пользователя
- Внутренние ссылки: каждая важная страница должна получать ссылки минимум с 5 других страниц сайта
- Интент запроса важнее плотности ключа: если топ заняли агрегаторы — одиночный сайт не победит за разумный срок

### 1.6 Конкурентный анализ

- Смотреть не только прямых конкурентов, но и тип доминирующих страниц в топе (агрегаторы, госсайты, Википедия — стратегия отличается)
- Для контентного анализа: TF-IDF, семантические кластеры, сравнение H2-структуры
- Инструменты: readpage.js (чистый текст), nlp_analyze.py (TF-IDF), seo-audit.js (технические параметры)
- Не сравнивать по слову «агрегатор vs лендинг» — это разные игры с разными правилами

## 2. Дизайн и UI/UX

### 2.1 Типографика

- Минимальный размер основного текста: 15–16px на desktop, 14px на mobile
- Межстрочный интервал: 1.5–1.7 для основного текста, 1.2–1.3 для заголовков
- Иерархия заголовков: H1 ≥ 28px, H2 ≥ 20px, H3 ≥ 16px — разница ощутима визуально
- Максимальная ширина строки: 65–75 символов (600–700px при 15px шрифте)
- Контрастность: минимум 4.5:1 для основного текста (WCAG AA)

### 2.2 Изображения

- Формат: AVIF первый выбор, WebP как fallback, JPEG/PNG только если нет поддержки
- LCP-изображение (первое видимое): `fetchpriority="high"`, `loading="eager"`, `<link rel="preload">`
- Все остальные изображения: `loading="lazy"`
- Alt-текст: описательный, не «image001.jpg», не спам ключей
- Размер файла: hero ≤ 100KB в AVIF, карточки ≤ 30KB, иконки — SVG или CSS
- Не использовать растровые иконки там, где есть SVG/иконочный шрифт
- Резкость: изображения не должны быть размытыми ни на retina, ни на обычных экранах — использовать srcset

### 2.3 Мобильная адаптация

- Mobile-first разработка: сначала мобильный вид, потом расширяем на desktop
- Тапабельные элементы: минимум 44×44px
- Горизонтальный скролл недопустим
- Модальные окна на мобилке: полный экран или bottom sheet, не маленькое окно с прокруткой
- Sticky-элементы на мобилке не должны перекрывать основной контент

### 2.4 Визуальная иерархия

- Одно главное действие на экран — не три CTA одинакового веса
- Белое пространство — не потеря места, а инструмент фокуса
- Цветовые акценты: не более 1–2 акцентных цветов на страницу
- Иконки: единая система, единый стиль — не мешать outline и filled в одном блоке
- Анимации: только если несут смысловую нагрузку; длительность ≤ 300ms для UI-переходов

### 2.5 Антипаттерны UI

- Эмодзи в UI-элементах (кнопки, заголовки, плашки) — заменять на иконки иконочного шрифта
- Текст поверх изображения без overlay — нечитаемо
- Фиксированные размеры в px для контейнеров — использовать max-width + %
- Placeholder вместо label — accessibility и usability нарушения
- Автофокус на мобилке — открывает клавиатуру, сдвигает контент

## 3. CRO-методология

### 3.1 Фреймворк аудита (LIFT)

- **Value Proposition**: ясно ли из первого экрана что предлагается и почему это ценно?
- **Relevance**: соответствует ли страница ожиданиям из объявления/поиска?
- **Clarity**: понятен ли следующий шаг без размышлений?
- **Anxiety**: что тормозит доверие (нет отзывов, нет лицензий, нет цен)?
- **Distraction**: что отвлекает от целевого действия?
- **Urgency**: есть ли причина действовать сейчас, а не завтра?

### 3.2 Принципы оценки гипотез

- Гипотеза = наблюдение + механизм + предсказание: «Если X, то Y, потому что Z»
- Приоритизация по PIE: Potential × Importance × Ease (1–10 по каждому)
- Гипотеза без данных — это мнение; помечать явно: «факт» / «гипотеза» / «не найдено»
- Минимальная выборка для A/B-теста: статистическая значимость ≥ 95%, минимум 2 недели

### 3.3 System 1 / System 2

- **System 1** (быстрое, автоматическое): первый экран, hero, CTA — должен работать за 3 секунды
- **System 2** (медленное, аналитическое): детали программы, FAQ, документы — для тех кто читает
- Социальные доказательства работают на System 1: цифры, фото, имена — не просто «отзывы клиентов»
- Цена без контекста = тревога; цена с раскладкой/сравнением = аналитика

### 3.4 A/B-тесты

- Тестировать одну переменную за раз
- Документировать: гипотеза → метрика победы → результат → вывод → следующий шаг
- Проигравший вариант не удалять сразу — зафиксировать почему проиграл

## 4. Контент и копирайтинг

### 4.1 Заголовки

- Заголовок отвечает на вопрос «что я получу?», не «кто мы такие»
- Конкретика > абстракции: «10 дней — готовый IT-проект» > «развитие ребёнка»
- Избегать педагогических и экспертных терминов в заголовках для массовой аудитории
- Длина H1 лендинга: 5–10 слов — помещается на один-два экрана смартфона

### 4.2 CTA

- Одна кнопка — одно действие, формулировка от первого лица: «Хочу записаться» > «Записаться»
- CTA выше сгиба всегда; повторять через каждые 2–3 смысловых блока
- Цвет CTA — акцентный, нигде больше не повторяется
- Микрокопия под кнопкой снимает тревогу: «без обязательств», «ответим за 10 минут»

### 4.3 Работа с персонами

- Аватар = конкретный человек с конкретной болью, не «наша аудитория 25–45 лет»
- Продаём через эмоцию покупателя, не через характеристики продукта
- Один лендинг = один аватар; если аудитории разные — разные страницы
- Язык аватара: использовать формулировки из реальных отзывов, не придуманные

### 4.4 Структура лендинга (порядок блоков)

1. Hero: оффер + ключевая выгода + CTA
2. Социальное доказательство (цифры, логотипы, рейтинг)
3. Проблема / боль аудитории
4. Решение + механизм
5. Как это работает (процесс/программа)
6. Результаты / трансформация
7. Доверие (команда, лицензии, гарантии)
8. Отзывы с именами и деталями
9. FAQ (снимает оставшиеся возражения)
10. Финальный CTA

## 5. Перфоманс и технический стек

### 5.1 Оптимизация изображений

- LCP-изображение: preload в `<head>`, `fetchpriority="high"`, разные размеры для mobile/desktop через `media`
- Все изображения в AVIF с WebP fallback через `<picture>`
- Lazy load для всего что ниже первого экрана: `loading="lazy"` + `decoding="async"`
- Размеры прописаны в HTML (width + height) — предотвращает CLS
- Не инлайнить base64 для изображений > 1KB

### 5.2 Core Web Vitals

- **LCP** ≤ 2.5s: оптимизировать hero-изображение, устранить render-blocking ресурсы
- **CLS** < 0.1: все изображения с размерами, шрифты с `font-display: swap`, динамический контент с зарезервированным пространством
- **INP** ≤ 200ms: тяжёлый JS в web workers или defer/async, не блокировать main thread
- Проверять в реальных условиях (field data), не только lab (Lighthouse)

### 5.3 Скрипты и аналитика

- Метрика / пиксели — только через стандартный async-тег, **не через Web Workers / Partytown**
- Сторонние скрипты: `defer` или `async`, после основного контента
- Критический CSS — inline в `<head>`, остальное — async load
- Никогда не блокировать рендер ради аналитики

### 5.4 Чеклист деплоя

- [ ] Сборка прошла без ошибок и предупреждений
- [ ] Проверка на dev-окружении перед проднем
- [ ] Скриншот до и после (diff визуальных изменений)
- [ ] Проверка мобильной версии
- [ ] Метрика/пиксели срабатывают (console проверка)
- [ ] Нет сломанных ссылок (404)
- [ ] Canonical, title, description на месте
- [ ] IndexNow / Sitemap отправлен после деплоя

## 6. Рабочие процессы и дисциплина

### 6.1 Гипотезы vs утверждения

- Факт — только подтверждённое данными или документацией (с источником)
- Гипотеза — явно помечать: «предположительно», «гипотеза», 🤔
- «Не найдено» — честный ответ, лучше чем додумать
- Любое утверждение об API, параметрах, полях — сначала документация, потом тест

### 6.2 Версионирование правок

- Коммиты — атомарные: одно изменение = один коммит с понятным сообщением
- Ветки: feature/ для нового, fix/ для исправлений, agent/ для агентов
- Никогда не пушить напрямую в main/prod без проверки на dev
- Перед деструктивными операциями — бэкап или возможность отката

### 6.3 Правила работы с агентом

- Указывать: конкретный файл/URL/компонент, ожидаемый результат, что **нельзя трогать**
- Запрещать касаться: файлы за пределами зоны ответственности, продакшн без явного разрешения
- Каждый агент работает только в своей ветке `agent/<задача>`
- Агент не мёрджит сам — создаёт PR и сообщает
- Инсайты из работы фиксировать в документацию — не держать в памяти сессии

### 6.4 Работа с данными

- Никогда не удалять данные с `permanently=true` без явного подтверждения
- Аналитические данные получать из API напрямую, не из кеша/ETL если ETL устарел
- Поведенческие метрики (bounce, scroll, time) — получать из Метрики + Clarity вместе, не из одного источника
- Тестовые данные (телефоны, заказы) — чётко маркировать, не смешивать с реальными

## 7. Антипаттерны — чего никогда нельзя делать

### SEO
- ❌ Создавать страницы под ключи без реальной частотности (Wordstat/GSC подтверждение обязательно)
- ❌ Дублировать title/description между страницами
- ❌ Description > 165 символов — обрезается в сниппете
- ❌ Title > 65 символов — обрезается в выдаче
- ❌ Конкурировать с агрегаторами/госсайтами за высокочастотные общие запросы без ссылочной массы

### Производительность
- ❌ Partytown или Web Workers для Метрики/аналитики — ломает цели и конверсии
- ❌ `permanently=true` в API удаления файлов — необратимо
- ❌ Inline base64 для изображений > 1KB
- ❌ Синхронные сторонние скрипты в `<head>`

### UI/UX
- ❌ Эмодзи в UI-элементах — только иконочный шрифт
- ❌ Три и более равнозначных CTA на экране
- ❌ Фиксированная ширина контейнеров на мобилке
- ❌ Placeholder вместо label в формах
- ❌ Анимации длиннее 500ms для UI-переходов

### Контент
- ❌ Педагогические термины (soft skills, фундамент, компетенции) в заголовках для потребительской аудитории
- ❌ Заголовок «О нас» или «Наша миссия» — пользователю важен он сам, не компания
- ❌ Общие слова без цифр: «много детей», «быстро», «качественно» — всегда конкретизировать

### Процессы
- ❌ Коммитить в main/prod напрямую без PR
- ❌ Делать вывод без данных и не маркировать его как гипотезу
- ❌ Начинать задачу не зафиксировав зону ответственности и критерий готовности
- ❌ Смешивать несколько изменений в один коммит

## 8. Прочее / Специфические инсайты

- **Позиции в Яндексе ≠ позиции в Google**: данные из Wordstat — это Яндекс; DataForSEO по умолчанию — Google. Всегда уточнять источник
- **Aggregator intent**: если топ-3 по запросу — агрегаторы, лучшая стратегия — IT/нишевая специализация, а не лобовая конкуренция
- **Clarity dimension1=URL**: работает только с `numOfDays=1–3`; при `numOfDays=7+` возвращает 400
- **DataForSEO live/advanced**: при локальном curl обрезается на ~15KB — запускать через Python requests или с сервера
- **Поведенческие метрики для Яндекса**: bounce rate и scroll depth влияют на ранжирование сильнее чем в Google — приоритет улучшения UX выше чем наращивание текстового объёма
- **GSC vs Яндекс.Вебмастер**: разные позиции для одних запросов — нормально; оптимизировать под Яндекс отдельно от Google
- **Schema FAQPage**: даёт сниппет в Яндексе и Google; добавлять на все лендинги с блоком вопросов/ответов — это конкурентное преимущество если конкуренты не используют
- **IndexNow**: после деплоя отправлять список изменённых URL — ускоряет переиндексацию в Яндексе
